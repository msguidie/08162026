## summary
The canonical minimal reference implementation of N-player AlphaZero, and the direct ancestor of the "value vector" design our Splendor agent needs. ~1200 lines of Python/PyTorch total. The single idea: replace AlphaZero's scalar value v with a length-N vector v⃗ (one expected utility per seat), have MCTS propagate the whole vector up the path unchanged, and have each node consume only its own mover's component (scores[current_player]) when updating its edge Q. This is exactly MCTS-max^n with a learned prior/value. Terminal states return a score vector ([1,-1,-1] for a P0 win in a 3-player game, [0,0,0] for a draw), and that same vector z⃗ is stamped onto every training position of the game as the value target — no per-player sign flip, no per-player relabelling. Evaluated only on two toy 3-player perfect-information games (Tic-Tac-Mo = 3-player 3x5 tic-tac-toe, and Connect3x3 = 3-player 6x7 connect-3). The mechanism is exactly what we want; the surrounding engineering (batch-1 inference, Python-thread self-play, ~11M-param SENet on a 3x5 board, unbounded replay, no arena gating, no batched leaf evaluation) is toy-scale and should not be copied. Notably the author's *earlier* repo petosa/simple-alpha-zero (Jan 2019) used the naive generalization — scalar v with adj_v = v if current_player == winning_player else -v (simple-alpha-zero/mcts.py:44), i.e. a paranoid "everyone-else-gets--v" backup — and multiplayer-alphazero (Oct 2019) is precisely the fix. That delta is the paper's contribution.

## algorithm
Standard AlphaZero policy-iteration loop, vectorized-ish with numpy, no loops in the selection step.

SEARCH (/tmp/claude-0/-home-user-08162026/6c4d3121-5cae-5177-9eec-d5961b7f3014/scratchpad/research/petosa_multiplayer-alphazero/mcts.py, 85 lines):
- Tree is a plain dict keyed by `s.tostring()` (mcts.py:21-22) — a transposition table, no parent pointers. Each entry is an object-dtype array `stats` of shape (num_legal_actions, 4) holding columns [action_index_tuple, N, Q, P] (mcts.py:56-59).
- Selection (mcts.py:32-38): `U = cpuct*P*sqrt(N.sum() + 1e-6)/(1 + N)`; `heuristic = Q + U`; `best_a_idx = np.argmax(heuristic)`. The 1e-6 "epsilon_fix" exists so that U is nonzero when all N=0, letting priors bias the very first visit (mcts.py:26-28). Note this is PUCT with sqrt(sum N) in the numerator, matching AlphaZero.
- Recursion (mcts.py:41-47): apply best action, recurse, then `v = scores[current_player]`, `Q <- (n*q+v)/(n+1)`, `N += 1`, and `return scores` (the FULL vector, untouched).
- Expansion (mcts.py:49-60): terminal check first (`check_game_over(s)` returns None or a score vector); if terminal return the score vector without inserting into the tree, so terminals are re-evaluated cheaply on every visit. Otherwise one NN forward pass, store priors P over the legal actions only, return v⃗.
- `get_distribution(s, temperature)` (mcts.py:65-83): π ∝ N^(1/T), with T→0 handled as argmax via the ZeroDivisionError/OverflowError catch, and a uniform fallback when every child is unvisited.

SELF-PLAY (trainer.py:26-69): one persistent MCTS tree per game (tree reused across moves within a game, never pruned); num_simulations per move; sample action from π; append [s, π, None]; at game end, `for i: data[i][-1] = scores` (trainer.py:66-67).

TRAINING (neural_network.py:24-37, 52-69): `train()` draws ONE minibatch of 64 with replacement from the whole buffer and takes ONE Adam step; `policy_iteration` calls it num_updates (=1000) times. Loss = `p_loss + v_loss` where `v_loss = ((v_pred - v_gt)**2).sum()` (neural_network.py:59) and p_loss is a Python for-loop over the batch computing -sum(π_gt * log_softmax(masked logits)) (neural_network.py:60-68). Legal-action masking is done with `torch.masked_select` on a boolean mask then log_softmax over only the valid entries (neural_network.py:73-81) — the same variable-length-legal-set trick we need for Splendor's 65-action space.

NETWORK (models/senet.py): pre-activation SE-ResNet, blocks [2,2,2,2], planes 64/128/256/512, global avg pool, then `p_head = Linear(512, prod(p_shape))` and `v_head = Linear(512, prod(v_shape))` with `v = torch.tanh(...)` (senet.py:91-92, 118-119). ~11.26M params per the author's own project page. models/senetbig.py is the same with blocks [3,4,6,3].

NO arena/gating: main.py:46-62 always trains on the newest net and checkpoints every `ckpt_frequency` iterations; `rank_checkpoints`/`one_vs_all` in experiments.py are post-hoc analysis, not a promotion gate.

## multiplayer_handling
THE CORE MECHANISM, exactly as implemented.

1) VALUE HEAD SHAPE. `v_shape = (game.get_num_players(),)` (neural_network.py:13) is passed into the model constructor; SENet emits `v = tanh(Linear(512, N)).view(batch, N)` (senet.py:92, 119). N independent tanh outputs in [-1,1]. There is NO softmax, NO sum-to-zero and NO sum-to-one constraint across the N components. Nothing in the algorithm requires zero-sum — which matters for us, see below.

2) SEAT INDEXING IS ABSOLUTE, NOT RELATIVE. v⃗[i] is "expected final score of seat i", in fixed seat order. The network is NOT given a canonicalized/rotated state; instead the whose-turn-it-is information is fed as N one-hot planes broadcast over the board (games/tictacmo.py:13-14 builds a 3x5x(3+3) tensor; take_action flips the indicator planes at tictacmo.py:26-28; get_player reads them back at tictacmo.py:46-48). Consequence: the net must learn seat symmetry from scratch, and there is no N-fold data amplification from rotating seats.

3) TERMINAL SCORE VECTORS. `check_game_over` returns None when the game is live, else a numpy vector indexed by player (game.py:16-21). Concretely (games/tictacmo.py:33-43): `reward = -np.ones(3); reward[p] = 1` → a P1 win is [-1,1,-1]; a full board is `np.zeros(3)` = [0,0,0]. Note these sum to -1, not 0 — the implementation is NOT zero-sum-constrained and does not care.

4) BACKUP (the whole trick), mcts.py:42-47:
       scores = self.simulate(s_prime)         # full length-N vector comes back
       v = scores[current_player]              # "Index in to find our reward"
       stats[best_a_idx, 2] = (n*q + v)/(n + 1)  # running mean Q for THIS edge
       stats[best_a_idx, 1] += 1
       return scores                           # vector passed up UNCHANGED
   `current_player = self.game.get_player(s)` (mcts.py:31) is the player to move at the PARENT node s, i.e. the owner of the edge being updated. So each node's Q column is measured in the currency of the player who moves at that node, and since selection is `argmax(Q + U)` over that node's own stats, every node greedily maximizes its own mover's component. That is textbook max^n / MCTS-max^n, and it drops out of two lines. No sign flipping anywhere; the vector is never negated, permuted or rescaled on the way up. Only ONE component of the vector is consumed per level — the rest are carried so ancestors can consume theirs.

5) TRAINING TARGET. trainer.py:66-67: the SAME final score vector z⃗ is written into every training row of the game, regardless of who was to move. Tuples are (s_i, π⃗_i, z⃗) — matching the paper's notation "(s_i, π⃗_i, z⃗) tuples since value is a vector" (WebSearch snippet). Combined with the absolute seat indexing and the turn planes in s, this is self-consistent: the net learns "given this board and whose turn it is, what does each seat finally score".

6) N-PLAYER TURN ROTATION. Handled purely inside each Game: `s[:,:,num_p+p] = 0; s[:,:,num_p+(p+1)%num_p] = 1` (tictacmo.py:27-28, connect3x3.py:32-33). MCTS is player-count-agnostic.

7) EVALUATION UNDER SEAT ASYMMETRY. play.py:8-38 with `permute=True` plays every permutation of the seat assignment (3! = 6 games per "match" for 3 players) and accumulates `scores[list(order)] += game_over`, so first/second/third-mover advantage is cancelled. experiments.py:15-22 pits one DeepMCTSPlayer against (N-1) UninformedMCTSPlayers at doubling strengths 10,20,...,1280 (main.py:60-62). Paper snippet confirms: "a total of 6 games is played between the same opponents — one game for each permutation of players to break any advantages from going first, second, or third."

8) TEAMS / CREDIT ASSIGNMENT: ABSENT. Zero support — grep for team/coalition/cooperative finds nothing. Every seat is an independent maximizer. There is also no backup rule variant (no paranoid, no offensive, no BRS, no mixing), no opponent modelling, and no tie-break policy when several actions share max heuristic beyond numpy's first-index argmax.

## hidden_info_handling
NONE, at every level, and it is not a small gap.

- game.py declares a fully-observable API: `get_initial_state()` returns THE state, `get_available_actions(s)`, `check_game_over(s)`, `take_action(s,a)`, `get_player(s)`. There is no information-set concept, no per-player observation function, no chance/nature node, no determinization, no belief state, no sampling of unknowns. Grep for hidden/imperfect/belief/determiniz/chance/stochast over the whole repo: zero hits.
- MCTS keys nodes on the raw full state bytes (`s.tostring()`, mcts.py:22), so a node IS a world state, not an information set. Two histories that are indistinguishable to the mover are still distinct search nodes only if the ground truth differs — and the search happily reads the ground truth when expanding.
- The network is fed the same full state s that the search uses, so an agent built this way would peek at the opponent's private information.
- The paper (per WebSearch snippets of the abstract) explicitly scopes itself to "two-player, deterministic, zero-sum games where perfect information of the game state is available" and generalizes only the player-count axis; it says nothing about imperfect information. I could not open the PDF to check the future-work section, so I cannot claim it discusses hidden information at all.

For our Splendor variant this means the repo answers our value-vector question completely and our hidden-info question not at all. Our two hidden components — deck order (a chance/nature source) and opponents' deck-reserved cards (private state) — need machinery from elsewhere (determinization/IS-MCTS, or the far simpler and probably right first move: treat the deck as a stochastic environment by shuffling a consistent deck at the root of each self-play game and giving the network only the acting seat's legal observation, i.e. train a "perfect-recall-of-my-own-info" net rather than a cheating net). Nothing in this repo helps you do that; copying its Game interface verbatim will silently build a cheating agent.

## training_recipe
CODE-VERIFIED (configs/tictacmo-gpu.json, configs/connect3x3-gpu.json, configs/tictactoe-gpu.json — all three are byte-identical apart from the game name and ckpt_frequency, so "the same hyperparameters are used across all games and experiments"):
- num_simulations (MCTS rollouts per move): 50. Same 50 at train time and at eval time.
- cpuct: 3.
- num_games (self-play games per policy iteration): 30.
- num_updates (Adam steps per policy iteration): 1000, each on a batch of 64 sampled WITH REPLACEMENT from the whole buffer (neural_network.py:27-28). So 64,000 sample-draws per iteration off ~30 games.
- batch_size: 64. lr: 1e-3, Adam. weight_decay: 1e-4 (coupled L2 inside Adam, not AdamW).
- buffer_size_limit: null in every config → UNBOUNDED replay buffer, never pruned (trainer.py:95-96 is a no-op).
- temperature: hard-coded 1 for the entire game, never annealed (trainer.py:75). Deviates from AlphaZero's T=1 for the first ~30 plies then T→0.
- Dirichlet noise: alpha=1, weight=0.25, applied at the FIRST MOVE OF THE GAME ONLY (trainer.py:33-34, 44-48 — `root` is set True once before the while loop and set False after the first move), and applied to the post-search visit distribution which is then ALSO stored as the policy target (trainer.py:47 then :50). AlphaZero instead adds noise to the root priors P before every move's search. Both the "once per game" and the "contaminates the label" parts are deviations.
- num_threads: 1 in the GPU configs; when >1, self-play games are farmed to `multiprocessing.dummy.Pool` (trainer.py:3, 80-86) — Python threads, GIL-bound, one independent tree each, shared NN.
- Inference: `predict` wraps a single state as `np.array([s])` (neural_network.py:43) — batch size 1 per simulation. No leaf batching, no virtual loss, no inference server.
- cuda: true wraps the model in `torch.nn.DataParallel` (neural_network.py:16-18), which is useless at batch 1.
- ckpt_frequency: 1 for TicTacMo/TicTacToe, 5 for Connect3x3. Evaluation after each checkpoint against uninformed MCTS at strengths 10,20,40,80,160,320,640,1280 (main.py:60-62).
- Network: SENet, PreActBlock [2,2,2,2], 64→128→256→512 planes, ~11.26M params. On a 3x5 board three stride-2 stages take 3x5 → 2x3 → 1x2 → 1x1 before the heads — extremely aggressive downsampling for a tiny board.

PAPER-REPORTED, SNIPPET-ONLY (arXiv PDF blocked — treat as low-confidence, single-source paraphrase):
- Training wall-clock: "about 18 hours" of self-play for Tic-Tac-Mo, and separately "about 18 hours" for Connect 3x3. No hardware named in any snippet I could retrieve, no iteration count, no sample count.
- Loss: "sum of cross-entropy loss and mean squared error", value head tanh in [-1,+1] — consistent with the code.
- No learning-rate schedule, no gating, no data augmentation (no board symmetries) appear anywhere in the code, and no snippet mentions any.

## reuse_for_us
Adopt the MECHANISM verbatim; discard the engineering. Concretely for the Splendor variant:

1) VALUE HEAD = length-N vector, tanh, no normalization across components. Ship one head sized to the max seat count (4) and mask/ignore unused seats, or instantiate per mode. The repo proves no zero-sum constraint is needed — which is exactly what our modes require, because "winner by excess" (1v2) and "team total > 30 plus second-score condition" (2v2) are not naturally zero-sum. Use continuous z in [-1,1] (e.g. tanh-squashed margin) rather than only ±1: the tanh head and the MSE loss support it unchanged, and it gives dense signal for the excess-based win conditions.

2) BACKUP = the two lines from mcts.py:44-47. Return the full vector, consume `scores[current_player]` at each node, never negate. This is the whole answer to "how do 3- and 4-player Splendor seats back up value".

3) TEAMS FALL OUT FOR FREE — this is the extension the repo doesn't make but is trivially implied. Keep the vector indexed by SEAT (length 4), and define z per seat as that seat's TEAM outcome:
   - 2v2: z = [T_A, T_B, T_A, T_B] (or whatever the seat→team map is). Then `scores[current_player]` at a node owned by a team-A seat already equals the team-A value, so both A seats maximize the same quantity and the max^n backup becomes cooperative with ZERO code change.
   - 1v2: z = [solo, duo, duo]. Same argument; the AI can be trained as the solo seat and as a duo member from the same net.
   - 2p / 3p / 4p individual: z = per-seat result.
   Do NOT collapse the vector to a length-2 "team value" — keeping it seat-indexed lets one net serve all four target agents and keeps the indexing identical to the repo's.

4) LEGAL-ACTION MASKING: copy `get_valid_dist` (neural_network.py:73-81) semantically — log_softmax over the legal subset only, for BOTH the prediction and the loss — but vectorize it. The repo's Python for-loop over the batch (neural_network.py:60-68) is fine at 15 actions and will dominate our step time at 65 actions × batch 1024. Use a fixed 65-wide logit tensor, add -1e9 at illegal positions, one batched log_softmax, and a masked KL. Same math, ~100x faster.

5) SEAT CANONICALIZATION — DEVIATE. The repo uses absolute seat order plus turn-indicator planes. For us, rotate the observation so the acting seat is index 0 and emit the value vector in ROTATED order; this gives an N-fold effective data multiplier and removes the seat-symmetry learning burden. Caveat specific to our rules: our seats are NOT interchangeable (1v2 solo is always seat 0 and always starts; the individual-mode tiebreak and the "final round ends when turn returns to the first player" rule privilege earlier seats), so keep an explicit "turn-order position" and "seats remaining this round" feature after rotating, and do not rotate across the solo/duo boundary in 1v2.

6) EVALUATION: steal play.py's `permute=True` seat-permutation match (play.py:11, 17, 33) wholesale — for 4-player that is 24 games per match, which is affordable and is the right way to kill seat bias in our asymmetric modes. Steal experiments.py's doubling-strength ladder (10→1280) against a search-only baseline as the primary "is it learning" curve; it needs no reference agent and is mode-agnostic.

7) UNIT-TEST IDEA FROM THE SIBLING REPO: petosa/simple-alpha-zero/tests/mcts_tests.py builds deliberately trivial games (OnePlayerGuessIt 2x2, TwoPlayerGuessIt, ThreePlayerLinearLeapFrog) whose search trees can be worked out by hand, then asserts the exact (N, Q, P) triple on every edge after each individual simulation. Build a "MiniSplendor" with a handful of actions and do the same — it is the only cheap way to prove the max^n backup and the 65-action mask are bit-correct before burning A100-hours.

8) THROUGHPUT — REPLACE ENTIRELY. batch-1 predict + GIL-bound thread pool + 11M-param SENet will not give us 2 s/move on a 4GB RTX 3060. For inference: small MLP/ResNet over a flat feature vector (Splendor has no meaningful 2D spatial structure — a conv tower is the wrong prior here), leaf-batched MCTS with virtual loss, fp16, target 400-800 sims in the 2 s budget. For training: 4xA100 DDP with a proper actor pool writing to a bounded replay buffer, not `np.concatenate` on an object array every iteration.

## ideas_to_steal
- The two-line max^n backup: return the full length-N score vector up the recursion untouched and consume only scores[current_player] into the edge Q (mcts.py:42-47). Player-count-agnostic, no sign flips, no special cases — this is the whole multiplayer contribution and it is 3 lines of code.
- One shared z⃗ target for every position in a game (trainer.py:66-67): the (s_i, π⃗_i, z⃗) tuple. No per-player relabelling, no separate nets per seat — one network serves every seat, which is exactly what we need for 2p/3p/4p/1v2/2v2 from one model.
- Nothing in the scheme requires zero-sum: terminal vectors in the repo sum to -1 for 3 players and it works fine. So our 'winner by excess' and team-total conditions can be encoded as continuous per-seat utilities in [-1,1] with no algorithmic change.
- Teams need zero new machinery — just set z_i to seat i's TEAM outcome and the max^n backup becomes cooperative automatically, because scores[current_player] is already the team value for every seat on that team. This is the natural extension to our 2v2 and 1v2 modes.
- Masked log_softmax over only the legal action subset, applied identically in predict and in the loss (neural_network.py:73-81) — the right pattern for our 65-action space where most actions are illegal most of the time.
- The epsilon_fix: sqrt(sum(N) + 1e-6) so U is nonzero at N=0 and priors bias the very first visit to a node (mcts.py:26-28, 35). Small, cheap, and meaningfully helps when the prior is good — relevant to us because a Splendor prior over 65 mostly-illegal actions is very informative.
- Seat-permutation matches (play.py:11,17,33) as the standard evaluation unit — play all n! seat orderings and sum, so first-mover advantage cannot flatter the agent. Mandatory for our seat-asymmetric modes.
- The doubling-strength search-only ladder (10,20,...,1280 sims) as a reference-free strength curve, plus a same-budget search-only control agent on the same ladder to isolate 'what did the network actually buy me' (experiments.py:15-22, 72-93, main.py:60-62).
- Terminal nodes are evaluated but never inserted into the tree (mcts.py:50-52) — they get re-derived on each visit, which keeps the transposition table clean and avoids stale terminal stats.
- From the sibling repo petosa/simple-alpha-zero: hand-computable toy games (2x2 'guess-it', 3-player 'leapfrog') with unit tests asserting exact per-edge (N,Q,P) after each individual simulation (tests/mcts_tests.py). Build the Splendor equivalent before scaling.

## pitfalls
- cpuct is NOT propagated into the recursion. mcts.py:42 calls `self.simulate(s_prime)` with no cpuct argument, so the configured cpuct=3 applies only at the root of each simulation and every deeper node silently uses the default cpuct=1. All published results were produced with this inconsistency. Pass it (or make it an attribute) in our port.
- Dirichlet noise is applied only at the FIRST move of each game, not at the root of every move (trainer.py:33-34, 44-48 — `root` is set False after one move), and it is added to the post-search visit distribution which is then stored AS THE POLICY TARGET (trainer.py:47 then :50) rather than to the root priors P before search. So it neither shapes the search nor stays out of the labels. Do it properly: perturb P at the root of every move's search.
- Dirichlet alpha=1 is a flat Dirichlet, not the spiky alpha<1 (0.03-0.3) AlphaZero uses; combined with weight 0.25 this is closer to uniform label smoothing than to targeted exploration.
- The value loss is `((v_pred - v_gt)**2).sum()` (neural_network.py:59) — summed over batch AND over the N value components, while the policy loss is summed over batch only. So the value:policy weighting silently scales with player count: our 4-player and 2v2 nets would get 2x the relative value weight of a 2-player net at the same batch size. Normalize by batch and by N, or weight explicitly.
- The logged training error is wrong. trainer.py:109 computes `(mean_loss*count + new_loss)/(count+1)` and DISCARDS the result — mean_loss is set once on the first update and never changed, so error_log records the loss of the first minibatch of each iteration, not the mean over 1000 updates. Every 'loss decreases and stabilizes' claim rests on this statistic.
- Q is initialized to 0 for unvisited edges (mcts.py:56 zeros). In an N-player game the typical terminal vector is [1,-1,...,-1], so a seat's expected value is strongly negative; Q=0 is therefore systematically optimistic and biases the search toward unvisited actions in a way that gets worse as N grows. Consider first-play-urgency (init Q to the parent's value) instead.
- A state with NO legal actions crashes. `idx = np.stack(np.where(available))` gives an empty (0,k) array, stats becomes shape (0,4), and the next selection visit hits `np.argmax` on an empty array → ValueError (mcts.py:34-37, 53-59). Our Splendor has exactly this case (10 tokens, 3 reserved, nothing affordable). We must define an explicit pass/no-op action in the 65-action space rather than an empty legal set.
- Absolute (non-canonicalized) seat indexing plus turn-indicator planes means the network must learn seat symmetry from data, forfeiting an N-fold data multiplier. Fine for 3-player tic-tac-toe with 18h of self-play; expensive for us.
- The MCTS tree is never pruned or re-rooted between moves within a game (trainer.py:28 creates it once) and the transposition dict keys on full state bytes — memory grows monotonically over a game and across a whole match for DeepMCTSPlayer (reset only between matches, players/deep_mcts_player.py:27-28). With Splendor's much larger state and longer games this is a real leak.
- Batch-1 inference (neural_network.py:43) inside a per-simulation Python recursion, with `DataParallel` wrapping (neural_network.py:16-18) that can never fill. Self-play parallelism is `multiprocessing.dummy` = GIL-bound threads (trainer.py:3, 80-86), and the GPU configs set num_threads=1 anyway. There is no virtual loss, no leaf batching, no inference server — this is the single biggest thing that will not scale to our 4xA100 training or 2 s/move 3060 inference.
- Unbounded replay buffer (buffer_size_limit: null in all three configs) with 1000 Adam steps x batch 64 = 64,000 draws per iteration off ~30 games (~360 positions for Tic-Tac-Mo). Extreme sample reuse and near-certain overfitting in early iterations; also `np.concatenate` on an object-dtype array every iteration is O(buffer) per iteration.
- Temperature is hard-coded to 1 for the entire game (trainer.py:75), never annealed toward 0 in the endgame — so late-game self-play moves stay noisy and the value targets are correspondingly noisier.
- No arena / no gating: main.py always continues from the newest net. Combined with an unbounded buffer this can absorb a regression silently; `rank_checkpoints` (experiments.py:26-48) is only run by hand afterwards.
- No board-symmetry augmentation anywhere, despite tic-tac-toe-family games having 8-fold dihedral symmetry. (Not applicable to Splendor, but it means the reported sample efficiency is not a tuned upper bound.)

# Rinascimento Framework (Bravi & Lucas, QMUL) — parameterised Splendor + Statistical Forward Planning + Event-Value Functions

## url
https://github.com/ivanbravi/RinascimentoFramework

## kind
Academic Java research framework (~350 source files) backing 4 papers: CoG'19 (arXiv 1904.01883, SFP agent tuning), GECCO'19 workshop (hyperparameter tuning), CoG'20 (arXiv 2006.05894, event-value functions) extended to IEEE ToG 15(1):16-25 2022, and ToG'22 (arXiv 2106.08371, MAP-Elites behaviour-space search). Paradigm is Statistical Forward Planning (RHEA / MCTS / OSLA) with hand-designed or evolved scalar heuristics, tuned by NTBEA. There is NO neural self-play, no policy/value network training, no AlphaZero. The neural nets present (Encog sparse MLPs) are tiny weight-vectors optimised by NTBEA, not trained by gradient descent.

## summary
Rinascimento is a fully parameterised Splendor engine plus a zoo of budget-limited forward-planning agents. Its real contributions for us are not the agents (which are weak and, as I verified by compiling and running the code, partly broken) but four design ideas: (1) determinization is free — every `State.copy()` reshuffles the remaining deck stacks, so each rollout is a fresh sample of hidden deck order; (2) the action space is never enumerated by agents — a weighted mixture of per-action-type *constructive* legal-move samplers (`RandomActionFeeder`) is the abstraction, so illegal actions never arise; (3) event-value functions: instead of scoring a state, you count the ~18 typed game events a player caused during a rollout and score that count-vector with a linear/polynomial function whose weights are optimised — a dense shaping signal that beats both raw points and hand-built state features; (4) two clean solutions to the "mutating a plan invalidates its suffix" problem in structured action spaces — branching mutation (resample the whole suffix) and seed-genomes (evolve RNG seeds, not actions). I independently measured the game: true rule-legal branching factor is ~32 (2p) / ~34 (4p) with a max of ~120-141, and games are ~80 ticks (2p, 40 turns/player) / ~142 ticks (4p, 35 turns/player). Best published agent (EF-id-poly,2) wins 65.4% on average in a 14-agent round robin and 59.5% vs the best point-heuristic RHEA.

## algorithm
FORWARD MODEL. `Engine.stepPlay(State)` (src/game/Engine.java:170-215). One tick = one atomic action; `playerId = state.getTick() % params.playerCount` — strict round-robin, no concept of "your whole turn". After every atomic action `passiveRules()` runs `TakeNoble` (src/game/action/passive/TakeNoble.java) for ALL players, then `gameOverCheck` ends the game IMMEDIATELY the moment any player reaches `endGameScore` (Engine.java:255-262) — there is no final round, unlike real Splendor and unlike our variant. Ties broken by fewer cards (`Result.comparator`, src/game/state/Result.java:24-34) — same as our tiebreak.

GAME PARAMETERS (src/game/Parameters.java:19-34, assets/*/parameters.json). playerCount, suitCount=5, coinCount (4 for 2p / 5 for 3p / 7 for 4p), goldCount=5, maxCoins=10, deckCount=3, cardsOnTableCount=4, noblesCount=playerCount+1, endGameScore=15, maxReserveCards=3, pickDifferentCount=3, pickDifferentAmount=1, pickSameAmount=2, pickSameMinCoins=4. Decks are 40/30/20 cards from CSV (assets/default/decks/*.csv), 10 nobles all worth 3 points (assets/default/nobles/nobles.csv) — same as our variant.

ACTIONS. Six types: BuyBoardCard, BuyReservedCard, PickDifferentCoins, PickSameCoins, ReserveBoardCard, ReserveDeckCard. Coin picks are a single signed delta vector over suits: positive = take from bank, negative = give back, so the over-cap discard is folded into the same action (src/game/action/active/pick/PickCoins.java:32-61). `PickDifferentCoins.canPerform` allows taking FEWER than 3 different (`takeCount > limit` is rejected, fewer is fine) — short takes are first-class. `PickSameCoins` requires the stack to hold >= pickSameMinCoins(4) and to take exactly `min(pickSameAmount, maxCoins - currTotal)`. Reserve grants 1 gold only if `goldStack>0 && coins+1 <= maxCoins` (ReserveBoardCard.java:75-83) — identical to our rule.

THE ACTION ABSTRACTION THAT MATTERS. There are two parallel action interfaces and only one is used. (a) A flat integer encoder `StatelessDecEnc` composing six `ActionType`s (Engine.defaultEngine(), Engine.java:296-320) — this is the "macro-action index space" you would expect; it is essentially unused (only `players/ai/general/DoNothingAgent` implements the int-based `GeneralPlayerInterface`). (b) `RandomActionFeeder` (src/game/action/random/RandomActionFeeder.java:53-67): a weighted mixture of six *constructive* generators, each of which builds a legal action of its type directly or returns null. `getAction` samples a generator by weight; on null it removes that generator and resamples; if all six fail it throws `StaleGameException`. Default weights BuyBoard 22.5 / BuyReserved 22.5 / PickDifferent 22.5 / PickSame 22.5 / ReserveBoard 5 / ReserveDeck 5. Every real agent calls `state.getRandomAction(playerId)`; so the agents' effective action space IS this sampler, i.e. a hand-set prior over move classes with rejection-free legal construction.

AGENTS.
- HyperRHEA "BM-RHEA" (src/players/ai/explicit/HyperRHEA.java): genome = array of *Action objects*, length `sequenceLength`, `evals` iterations of a (1+1) elitist hill-climber (accept if `mutationFitness >= solutionFitness`, line 109). `mutationStyle` 0 = full random restart, 1/2/3 = BRANCHING MUTATION: pick a mutation point (uniform / exponential-decay / Gaussian), keep the prefix, and resample every action from that point on while forward-simulating (lines 150-195) — the fix for "changing action i makes actions i+1.. illegal". `pickReturnAction` scans the plan for the first action still legal in the real state and falls back to a random action (lines 232-244). Shift buffer supported.
- SeedingRHEA "SRH" (src/players/ai/seeding/SeedingRHEA.java): genome = `long[]` of RNG SEEDS; each seed is fed to `getRandomAction(playerId, seed)` which reseeds the feeder. Because a seed decodes to a legal action in ANY state, the genome can never go illegal. Mutation = replace a seed with a fresh `random.nextLong()`. Fitness = delta of heuristic over the plan, optionally discounted (lines 127-183).
- MCTSPlayer / MCTSRootNode (src/players/ai/explicit/mcts/): OPEN-LOOP MCTS — nodes store only an action, the state is re-simulated from the root each iteration (`search`, MCTSRootNode.java:106-119). `expand` samples `progressionSize` random actions and adds the unseen ones; `expansionProbability` (0.2) re-expands an already-populated node instead of descending — progressive widening by coin flip. Reward is `h.value(endOfRollout) - h.value(root)`, a potential-style delta, not win/loss. Recommendation: max / robust / secure child.
- OneStepLookAheadAgent: intended greedy 1-ply; actually broken (see pitfalls).
- Heuristics (src/game/heuristics/): PointsHeuristic (own points), PositionHeuristic/WinHeuristic (1 if finished 1st), PointsPositionHeuristic (points while running, `100 + n - position` when over), plus the two learned families below.

EVENT-VALUE FUNCTIONS (the CoG'20 / ToG'22 contribution). Every state mutation fires a typed event through `RinascimentoEventDispatcher` (src/game/log/RinascimentoEventDispatcher.java). 18 event types (src/game/log/converters/IdentityConverter.java): nobleTaken, increase/decreaseTokens, increase/decreaseGold, drawCard, fillCard, fillNoble, increase/decreasePlayerTokens, increase/decreasePlayerGold, reserveHiddenCard, reserveBoardCard, receiveNoble, receiveCardBonus, receiveCardPoints, receiveNoblePoints. `SimpleConverter` collapses these to 5 hand-crafted features: take token, reserve hidden, reserve board, receive noble, receive points. `PlayerEventVectorLogger` keeps only events whose actuator equals the agent's own name and counts them per type; `LogBasedVectorHeuristic.ground()` resets the counter and attaches it to the rollout state, and `value()` returns `WeightedHeuristic(countVector)` — a linear dot product, a homogeneous polynomial of order k (all C(n+k-1,k) monomials), or a small Encog MLP. So the "value" of a rollout is a learned function of WHAT HAPPENED, not of the end state. Concrete tuned 5-feature EF (agents/R2-NTBEA-best.json, "linear^5"): take token +0.2, reserve hidden +0.2, reserve board -0.4, receive noble -0.6, receive points +0.8.

MAP-ELITES (ToG'22). `mapelites/` searches the SAME agent+EF hyperparameter space but archives by 8 behaviour descriptors (assets/_setup/8_behaviours.json): card count [0,40], nobles [0,4], total coins [0,120], reserved cards [0,30], card-bought deck [0,2], card cost [0,15], game duration [0,300], points [0,25], each on a 60-bin axis; fitness = win rate vs a fixed opponent over 20 games (src/mapelites/FitnessFunction.java:22, 82).

## multiplayer_handling
There is NO value vector and NO team support anywhere in the codebase — this is the single biggest gap versus our 1v2 / 2v2 requirements.

Value is a scalar for the acting seat only: `Heuristic.value(BudgetExtendedGameState state, int playerID)` (src/game/heuristics/Heuristic.java:7). MCTS backs up `h.value(state,playerID) - h.value(originalState,playerID)`; RHEA maximises `h.value(finalState, myId)`. Opponents' scores never enter the objective except implicitly through PositionHeuristic/PointsPositionHeuristic, which use `Result.position[playerID]` — a rank, so it does encode "beat everyone" but still collapses to one number.

N players are handled by *explicit opponent models inside the forward model*, not by a multi-head value:
- `MCTSRootNode.rollFullTurn` (lines 235-247) applies my action then loops `pID = (playerID+1) % playersCount` until it wraps, asking each opponent model for one action — so one tree edge = one full round of the table.
- `HyperRHEA.randomPlan/mutate/playPlanWithOpponents` use the same nested `for(pId...)` pattern, so each genome slot is my action in one round and the opponents fill the gaps.
- Opponent model choice is a tuned hyperparameter: 0 = DoNothingAgent, 1 = SafeRandomPlayer, 2 = OneStepLookAheadAgent (`prepareOpponents`, HyperRHEA.java:59-74; `factories` in MCTSRootNode.java:37-41).
- Opponent models get a *fraction* of the search budget via `copyForPlayerAndSplit(pId, opponentBudgetRatio)` — `Budget.split` creates a child budget that also decrements the parent (src/game/budget/Budget.java:17-35), so opponent modelling is charged against the agent's own 1000-call budget. Tuned ratios are tiny: 0.005-0.05.

Crucially, tuning drove agents AWAY from opponent modelling: BMRH* (agents/R1-NTBEA-best.json params [1,1,3,1,1,0,2,2,1,0]) has opponentType=0 (DoNothing) and sequenceLength=2; the paper text states "the agents are configured to not model opponents, probably because having a weak model introduces more noise reducing the overall budget significantly", and "both BMRH* and SRH* evolv[e] sequences of just 2 actions and MCTS* grow[s] a tree of maximum depth 2". The second-round BMRH** does use opponentType=1 (SafeRandom) with sequenceLength=3.

Credit assignment: the win adapter `RWonStaleLossAdapter` (src/game/adapters/RWonStaleLossAdapter.java) returns WON=1 for a sole 1st place, TIE=2 for a shared 1st, STALE=0, and `-position+1` (0, -1, -2 ...) otherwise — a per-seat scalar with no team aggregation. `Engine.shufflePlayers=true` (Engine.java:41) randomises seat order every game so seat bias is averaged out; NTBEA always slots the candidate into the last seat (`RinascimentoAgentEvaluator.createPlayersList`) and relies on that shuffle.

Practical implication for us: nothing here transfers directly to 1v2 or 2v2. We would have to add a value vector (or team-sum value) ourselves; Rinascimento's only lever is "choose which opponent model to simulate", which is exactly the wrong abstraction for a cooperative duo.

## hidden_info_handling
Two mechanisms, one elegant and one broken.

1. DETERMINIZATION ON COPY (the good idea). `State.reshuffleOnCopy = true` (src/game/state/State.java:25) and `State.copy()` lines 448-453: for every deck, `copy.deckStacks[deckId] = this.deckStacks[deckId].clone(); if(reshuffleOnCopy) copy.deckStacks[deckId].shuffle();`. `ShuffledDeck` is a `Stack<Integer>` of remaining card ids, so cloning preserves the exact multiset of unseen cards (cards on the board and cards already reserved from a deck have been popped) while randomising their order. Every agent already calls `gameState.copy()` per rollout, so each rollout is automatically a fresh determinization of hidden deck order — no separate PIMC/IS-MCTS machinery. Cost is O(deck size) per copy, done thousands of times per move.

2. HIDING OPPONENT INFORMATION (intended but non-functional at HEAD). `State.copyForPlayer(playerID)` (State.java:124-137) copies the state and calls `filterReservedCards()` on every OTHER player, which erases reserve slots whose `reservedIsVisible[i]` is false (src/game/state/PlayerState.java:106-114). `Engine.stepPlay` hands every agent `state.copyForPlayer(playerId)`, so the plumbing is right. BUT `PlayerState.reserveHiddenCard` sets `reservedIsVisible[position] = true` (PlayerState.java:176) — the commented-out original at src/game/action/active/reserve/deck/ReserveDeckCard.java:60 shows the intent was `= false`. Consequence: deck-reserved cards are marked visible, `filterReservedCards()` never erases anything, and **every agent sees every opponent's face-down reserved card**. This is exactly the piece of hidden information our variant also has (opponents' deck-reserved cards), and Rinascimento silently does not model it.

3. Board, nobles, coin stacks, and all players' gems/points/tokens are fully public in the copy. Card identities on the board are public. The `reserveHiddenCard` vs `reserveBoardCard` distinction survives in the EVENT stream (types 12 vs 13 in IdentityConverter), so an EF can still weight "I reserved blind" differently from "I reserved from the board" — and the tuned linear^5 does exactly that (+0.2 vs -0.4).

4. No belief state, no inference over opponents' hands, no information-set abstraction. The whole approach is: reshuffle unseen cards, roll forward, average over many rollouts.

## training_recipe
There is no gradient training. Everything is NTBEA (N-Tuple Bandit Evolutionary Algorithm, lib/ntbea.jar) over a discrete hyperparameter space; the "learned" objects are agent hyperparameters plus discretised heuristic weights.

Depth/rollout budgets are consumed by `BudgetExtendedGameState.perform()`, so tree depth x width x opponent-model calls all draw on the same 1000.

## reuse_for_us
DIRECTLY REUSABLE.

1. Determinization-on-copy. Our Python engine should reshuffle the unseen-card multiset on every root copy (or every N rollouts) exactly as `State.copy()` does. It is ~5 lines and gives correct hidden-deck handling with no PIMC machinery. Because our board-reserved cards are public and only deck order + opponents' deck-reserves are hidden, the same trick covers both: keep an "unseen pool" = deck remainder + opponents' hidden reserves and resample it per rollout. Fix the bug they have — actually mark deck-reserved cards hidden.

2. Event-value functions as AUXILIARY HEADS. This is the highest-value idea. Rather than only training win/value, add auxiliary prediction targets that are counts of typed events attributable to each seat over the next k plies: tokens gained, gold gained, card bought by tier, card reserved (board vs deck), noble taken, points from cards, points from nobles, tokens spent. In Splendor the point reward is extremely sparse (I measured ~40 turns per player at 2p with 15 points to win), and the CoG'20 result — EF 65.4% vs SF 40.5% average in a like-for-like tournament — is direct evidence that an event-count signal is a better learning target than a state-feature signal in THIS game. Use it as (a) auxiliary loss heads on the AZ trunk, and (b) a shaped bootstrap value for the first generations before self-play win signal is informative.

3. Calibration numbers for our engine. Their 2p legal BF is ~32 against our 65-action space; ours is larger mainly because we enumerate all 30 gem takes and 15 buys/reserves as fixed slots. Expect ~30-35 legal actions per state at 2p, and ~40 turns per player -> ~80 plies per 2p game. That sizes replay buffers, MCTS sim counts, and per-game NN eval counts. Their 300-tick stale timeout maps to our need for a hard ply cap.

4. Legal-move sampling prior. Their weighted per-class sampler is a hand-set action prior. Our policy head plays that role, but the class weights (buy 22.5, buy-reserved 22.5, take-different 22.5, take-same 22.5, reserve-board 5, reserve-deck 5) are a sensible Dirichlet prior / rollout policy for the earliest untrained generations and for any non-NN baseline opponent we need.

5. Structured-action mutation, if we ever want a cheap non-NN baseline or an opponent-diversity pool: BM-RHEA with branching mutation at sequenceLength 2-3 and 200 evals is ~40 lines and beats random 96%+ of the time. It is also a good sanity opponent for measuring our AZ agent's strength on an absolute scale.

6. Seat handling. `Engine.shufflePlayers=true` — randomise seat assignment every self-play game so the network cannot exploit seat priors. For our 1v2 mode, where seat 0 always starts, we must instead explicitly balance which side the learner plays.

DO NOT REUSE: the flat `ActionsEncoderDecoder` (broken, see pitfalls), the MCTS implementation (broken UCT), OSLA (broken), the "abort the whole game when one player is stuck" stale rule, and the immediate game-over-on-15 rule (we have a proper final round).

GAPS WE MUST FILL OURSELVES: value vectors / team credit for 1v2 and 2v2 (Rinascimento has nothing), noble CHOICE when several qualify (their TakeNoble auto-takes the first qualifying noble in index order and applies to all players after every action), and the no-legal-move-is-a-pass rule.

## ideas_to_steal
- Determinization for free: reshuffle the remaining-deck stack inside the state copy constructor (State.java:451-452, reshuffleOnCopy=true) so every rollout automatically samples a fresh hidden-card order with no separate PIMC/IS-MCTS code path.
- Event-value functions: score a rollout by a weighted function of the COUNTS of ~18 typed game events the player caused (tokens gained, gold gained, reserve-hidden, reserve-board, noble received, card points, noble points, ...) instead of by the end state. Dense signal for a sparse-reward game; use as auxiliary prediction heads on our AZ trunk and as an early-generation shaped value.
- Two-level event vocabulary: a full 18-type identity converter and a hand-crafted 5-feature collapse (take token / reserve hidden / reserve board / receive noble / receive points, SimpleConverter.java). Gives a cheap knob to trade feature richness against sample efficiency; the 18-type version won.
- Branching mutation for structured action genomes (HyperRHEA.mutate, lines 150-195): when you change action i in a plan, resample i+1..n while forward-simulating, because prefix changes invalidate the suffix. Directly applicable to any sequence-level search over Splendor actions.
- Seed genomes (SeedingRHEA): evolve long[] RNG seeds instead of actions; a seed always decodes to a legal action in any state, so the genome is state-independent and never illegal. Clean trick, though empirically weak here (14% vs BM-RHEA).
- Constructive legal-action sampling with resample-on-null: pick an action CLASS by weight, construct a legal instance of it directly, and if that class has no legal instance drop it and resample among the rest (RandomActionFeeder.java:53-67). Never generates an illegal action, never needs a mask over a huge flat space, and doubles as a tunable action prior.
- Fold the over-cap token return into the take action as one signed delta vector over suits (PickCoins.java) rather than a separate discard phase. Our variant makes over-cap takes illegal, but the same encoding cleanly expresses forced short takes.
- Charge opponent-model simulation against the agent's own search budget via a splittable budget object that decrements its parent (Budget.java:17-35). Makes 'how much compute do I spend predicting opponents' a tunable hyperparameter with honest accounting.
- Potential-shaped MCTS reward: back up h(end of rollout) - h(root) rather than an absolute value (MCTSRootNode.java:113). Useful whenever the heuristic has an arbitrary offset.
- One noisy game per hyperparameter evaluation and let the bandit model average (RinascimentoAgentEvaluator.java:76). If we tune AZ hyperparameters with NTBEA-like methods, do not waste budget on low-variance per-config estimates.
- MAP-Elites over agent hyperparameters archived by 8 gameplay behaviour descriptors (card count, nobles, total coins, reserved cards, deck-of-card-bought, card cost, game duration, points; 60 bins each) to produce a DIVERSE opponent pool and to detect degenerate game designs. A ready-made recipe for generating varied sparring partners for our league and for validating our custom rule set.
- Always randomise seat order across self-play games (Engine.shufflePlayers=true) so the net cannot learn a seat prior.

## pitfalls
- THE FLAT ACTION ENCODER IS BROKEN AND MUST NOT BE COPIED. ATPickSameCoinsGeneric.createAction (lines 22-39): with base=2 in the normal branch, transpose(pattern,2) maps digit 0->2 and digit 1->1, then the 1s are overwritten with pickSameAmount=2, so ALL 32 action ids decode to [2,2,2,2,2], which fails canPerform (takeCount 5 > 1). I verified empirically: at a fresh 2p state the encoder yields ZERO legal take-2-same actions. Legal pick-same only ever appears through the over-cap branch.
- The encoder's decodeActionId (ATPickDifferentCoinsGeneric.java:51-59) uses Integer.toString(id, base) and writes digits LEFT-ALIGNED into the vector. It is not injective (ids 1, 2, 4, 8, 16 all decode to [1,0,0,0,0]) and, because Java never emits leading zeros, it can only produce patterns whose first entry is non-zero. I verified: of 32 pick-different ids only 17 distinct patterns appear and only 12 are legal, ALL of which take coin suit 0 (plus a legal no-op [0,0,0,0,0]). The encoder literally cannot express 'take suits 1,2,3'. Measured flat index space is ~2000 wide while true legal BF is ~32.
- The framework only works because no real agent uses that encoder — every agent calls state.getRandomAction(). Anyone porting 'the Rinascimento action space' to a policy head would inherit a broken, mostly-illegal, non-injective space.
- MCTS UCT has a missing-braces bug (MCTSRootNode.java:201-208): 'if(currUcb>bestUcb) bestUcb = currUcb; child = currChild;' — the assignment to child is outside the if, so uct() always returns the LAST child in the list regardless of UCB. The published MCTS results are for an agent whose selection is effectively arbitrary.
- OneStepLookAheadAgent is a no-op: 'Action newAction = getRandomAction(...); do { ... } while(newAction != null);' never reassigns newAction (OneStepLookAheadAgent.java:26-34), so it re-evaluates one random action until the budget throws and returns it. I confirmed by running 400 fixed-seat games: OSLA vs Random 51.8% vs a 48.3% Random-vs-Random baseline. Any paper number involving OSLA (including its use as opponent model type 2) is measuring a random agent.
- Hidden reserves are not hidden. PlayerState.reserveHiddenCard sets reservedIsVisible[position]=true (PlayerState.java:176) instead of false, so copyForPlayer's filterReservedCards() never erases anything. The partial-observability claim in the papers is not realised by this code at HEAD.
- Event-value agents silently score 0 if no RinascimentoEventDispatcher is attached to the state (the default is DummyStateEventDispatcher, State.java:52). LogBasedVectorHeuristic.value() reads an all-zero counter and returns 0 for every candidate, degrading the agent to random — measured at 2.0% vs BMRH*. Any auxiliary-signal plumbing needs a loud assertion, not a silent default.
- A single stuck player kills the whole game: RandomActionFeeder throws StaleGameException and Engine.stepPlay marks the ENTIRE game stale with everyone at position -1 (Engine.java:186-190). I measured 2.0% stale at 2p and 11.0% at 3p/4p — driven by the bank being fully drainable (coins+gold 30 vs 3x10, 40 vs 4x10). Our variant's rare no-legal-move seat must be a pass, not a game abort, or ~10% of our self-play games become garbage.
- Game ends the instant anyone hits 15 (Engine.gameOverCheck, lines 255-262) — no final round. Their reported win rates therefore encode a strong first-to-15 race dynamic that does NOT match our rules; do not transfer strategic conclusions (e.g. 'short horizons suffice') without re-testing under a proper final round.
- TakeNoble is automatic and applies to ALL players after EVERY atomic action, taking the first qualifying noble in index order with no player choice (TakeNoble.java:13-32). Our variant lets the player choose among several qualifying nobles, so noble policy is a real decision for us and a non-decision for them.
- NTBEA fitness is one game per evaluation. Reported 'best configurations' are the argmax of an extremely noisy model; the CoG'20 protocol needed 100 independent NTBEA repeats plus a 1000-game validation to get stable answers. Treat any single tuned config from agents/*.json as a sample, not a recipe.
- The tuned MCTS config in agents/R1-NTBEA-best.json is [0,0,0,1,3,0,0,2,0] = exploration constant 0.0, depth 1 — the tuner collapsed MCTS to a degenerate greedy sampler. Combined with the UCT bug, 'MCTS is competitive with RHEA in Splendor' is not a claim I would rely on.
- Zero support for teams, value vectors, or asymmetric win conditions. All heuristics are scalar-for-one-seat. Our 1v2 (solo 15 / duo 34 combined, winner by excess) and 2v2 (team total > 30 plus a second-score condition, revocable) need value machinery that simply does not exist here.

# opendilab/LightZero — Gumbel AlphaZero / Gumbel MuZero (board-game MCTS stack)

## url
https://github.com/opendilab/LightZero

## kind
code repository (Apache-2.0), with an accompanying NeurIPS 2023 Datasets & Benchmarks spotlight paper; studied at commit 9ccf29b (2026-08-28), version 0.2.0

## summary
LightZero is a DI-engine-based unified MCTS/AlphaZero/MuZero benchmark (~82k LOC in lzero/, ~14k in zoo/board_games/). It contains two Gumbel implementations. (1) Gumbel MuZero — the maintained one: learned model, C++/Cython tree (lzero/mcts/ctree/ctree_gumbel_muzero/lib/cnode.cpp, 1152 lines), batched across roots, faithful transliteration of DeepMind mctx's sequential-halving tables. (2) Gumbel AlphaZero — a real-model variant (lzero/policy/gumbel_alphazero.py, 440 lines + lzero/mcts/ctree/ctree_gumbel_alphazero/mcts_gumbel_alphazero.cpp, 762 lines) that is effectively abandoned: added 2024-04-10 (PR #212), touched once since (a 2026-08-24 memory-leak sweep), absent from the README support matrix, zero tests, zero CI coverage, no Python fallback, and a build script whose paths are literally `/Users/<your_user_name>/...`. Both are hard-wired to exactly two players with scalar negamax values; Gumbel MuZero's backprop cannot even do two-player self-play (`assert(to_play == -1)`). Every Gumbel board-game config in the repo (3 of them) is `play_with_bot_mode`; no self-play Gumbel config exists. Chance nodes exist only in a separate StochasticMuZero policy (learned VQ chance encoder, single-player, never combined with Gumbel). Nothing addresses hidden information. For our 65-action, up-to-4-player, chance-node Splendor variant the framework is not reusable, but ~180 lines of its Gumbel math and one architectural pattern (batched lockstep trees) are worth lifting.

## algorithm
Gumbel AlphaZero (lzero/policy/gumbel_alphazero.py + ctree_gumbel_alphazero/mcts_gumbel_alphazero.cpp): a real-model AlphaZero where the C++ tree drives a live Python env object. Per move: `env.reset(start_player_index, init_state, ...)`, expand root via `policy_forward_fn(env)` -> (dict{legal_action: prob}, value), add Dirichlet noise, then for n in range(num_simulations): reset the env again from init_state and descend. Root child selection = Gumbel sequential halving (`_select_root_child`, line 146): build `table_of_considered_visits(max_num_considered_actions, num_simulations)`, index it by `sum(child visit counts)`, and argmax `score_considered = max(-1e9, gumbel[i] + prior[i] + penalty[i] + sigma(completed_q)[i])` (line 394). Interior selection (`_select_interior_child`, line 185) = argmax of `prior + completed_q - visits/(1+sum_visits)`. Completed Q (`_qtransform_completed_by_mix_value`, line 257) fills unvisited children with the mixed value `(raw_value + N*sum_a pi_a q_a / sum_a pi_a) / (1+N)`, min-max rescales, then scales by `(maxvisit_init + max_visits) * value_scale`. Backup is scalar negamax (`node_gumbel_alphazero.h:31-46`: self_play_mode negates the value at each parent; play_with_bot_mode does not). Training target: `_get_improved_policy(root)` (line 547) = `softmax(prior + completed_q)` scattered over the full action space; loss = `F.kl_div(log softmax(net_policy), improved_probs)` + `mse(value, ±1 outcome)` + entropy bonus (gumbel_alphazero.py:205-212).

Gumbel MuZero (ctree_gumbel_muzero/lib/cnode.cpp): same math but over a learned latent model, and batched — one `batch_traverse` descends all `batch_size` roots to leaves, one `model.recurrent_inference` call per simulation across the whole batch, then `batch_back_propagate` (lzero/mcts/tree_search/mcts_ctree.py:1088-1184). `score_considered` (cnode.cpp:1096) and `get_sequence_of_considered_visits` (cnode.cpp:1041) are line-for-line ports of mctx `seq_halving`.

Deviations from the reference (mctx, verified against https://raw.githubusercontent.com/google-deepmind/mctx/main/mctx/_src/{policies,action_selection}.py):
- mctx samples gumbel per search: `rng_key, gumbel_rng = jax.random.split(rng_key); gumbel = gumbel_scale * jax.random.gumbel(gumbel_rng, shape=root.prior_logits.shape)`. LightZero hard-codes `gumbel_scale = 10.0; gumbel_rng = 0.0` inside the C++ CNode constructor (ctree_gumbel_muzero/lib/cnode.cpp:61-63 and 86-89) — the same deterministic Gumbel vector for every root of every game, never re-seeded, never read from config. mctx's default gumbel_scale is 1.0.
- mctx adds `root.prior_logits` (raw network logits). LightZero adds the softmax *probability* (`prior = policy[a]/policy_sum`, cnode.cpp:143-146; AlphaZeroModel.compute_policy_value returns `softmax(logit)`, lzero/model/alphazero_model.py:185). With gumbel_scale=10 (gumbel std ≈ 12.8) against a prior term bounded in [0,1] and a Q term of range ≈0-5, the prior is effectively erased from root selection.
- mctx plays the sequential-halving winner `masked_argmax(score_considered(...))`. LightZero's collect path takes `np.argmax(improved_policy_probs)` (lzero/policy/gumbel_muzero.py:589-591) and computes-then-discards the `select_action` result — so collect-time Gumbel exploration is gone; only Dirichlet root noise remains.

## multiplayer_handling
Exactly two players, everywhere, with a scalar value and negamax sign-flipping. No value vectors, no teams, no coalitions, no >2 support of any kind (`grep -rn "num_players|multi_agent|n_players|value_vector|per_player" lzero/` returns nothing).

Hard evidence:
- `assert(to_play == -1 || to_play == 1 || to_play == 2);` — lzero/mcts/ctree/ctree_muzero/lib/cnode.cpp:431. `players = 1` if to_play==-1 else `players = 2` — same file lines 776-781; mirrored in lzero/mcts/ptree/ptree_mz.py:456-458.
- Negamax backup: ctree_muzero/lib/cnode.cpp:458-476 (`if (node->to_play == to_play) value_sum += v else value_sum += -v`); lzero/mcts/ptree/ptree_az.py:76-99 and 331-341 (`node.update_recursive(-leaf_value, negate=True)`); ctree_gumbel_alphazero/node_gumbel_alphazero.h:31-46.
- Every board env: `self.players = [1, 2]` — tictactoe_env.py:89, gomoku_env.py:150, connect4_env.py:128 and 314, chess_lightzero_env.py:25, chinese_chess_env.py:103. The "add your own game" template zoo/board_games/tictactoe/envs/dummy_any_game_env.py:77-82 offers only `self_play_mode` (players=[1,2]) or `single_player_mode` (players=[1]).
- Credit assignment is 2-player zero-sum: lzero/worker/alphazero_collector.py:363-383 `reward_shaping` sets `t['reward'] = int(reward) if t['obs']['to_play'] == to_play else int(-reward)`.
- Gumbel MuZero cannot even do 2-player self-play: `cback_propagate` begins `assert(to_play == -1);` and does a plain single-player bootstrap with no sign flip (ctree_gumbel_muzero/lib/cnode.cpp:605-631), and `cbatch_traverse` never alternates `virtual_to_play_batch` while descending (cnode.cpp:834-897) — contrast ctree_muzero/lib/cnode.cpp:883-890 which does flip 1<->2. setup.py adds no explicit `-DNDEBUG` (setup.py:49-59) but Python's default build CFLAGS normally do, so that assert is likely compiled out and self-play would silently produce wrong values.
- Consistent with the above: `grep` over the whole repo shows all three Gumbel board-game configs are `battle_mode='play_with_bot_mode'` (gomoku_gumbel_alphazero_bot_mode_config.py, gomoku_gumbel_muzero_bot_mode_config.py, tictactoe_gumbel_muzero_bot_mode_config.py, plus the two agent-config mirrors). There is no `*_gumbel_*_sp_mode_config.py` anywhere.

"Battle mode" evaluation is not a league. The three modes (docs/source/tutorials/envs/customize_envs.md:169-174, connect4_env.py:207-297) are: `self_play_mode` (one agent plays both seats, env steps once, MCTS alternates to_play), `play_with_bot_mode` (env internally steps a scripted rule/alpha-beta bot after the agent and sets `to_play = -1`, turning it into a single-player MDP), and `eval_mode` (same, opponent may be a human at the CLI). There is no Elo, no opponent pool, no historical-checkpoint play — `grep -rin "league|elo|opponent_pool"` returns nothing. Evaluating against a previous checkpoint is not supported out of the box.

## hidden_info_handling
None. There is no determinization, no ISMCTS, no information-set abstraction, no belief model, and no notion of a private observation anywhere in the repo. The AlphaZero-family MCTS assumes perfect information by construction: the C++ tree calls `simulate_env.reset(start_player_index, init_state, ...)` once per simulation with `init_state` = the fully observable board array (`py::bytes(init_state.attr("tobytes")())`, mcts_gumbel_alphazero.cpp:485-499), then replays the tree descent with real `env.step(action)` calls.

The only stochasticity support is StochasticMuZero (lzero/policy/stochastic_muzero.py + lzero/mcts/ctree/ctree_stochastic_muzero/lib/cnode.cpp), which alternates decision nodes and chance nodes (`is_chance`, `chance_space_size` default 2, cnode.cpp:66-67, 96-165; chance branch sampled from the prior outcome distribution at cnode.cpp:610-632) with a learned VQ-style chance encoder over consecutive-frame pairs (stochastic_muzero.py:391-405), optionally supervised by a true chance label (`use_ture_chance_label_in_chance_encoder`). That handles *stochastic transitions in a learned model*, not *hidden state*. It is never combined with Gumbel, never combined with board_games/two-player, and all five of its configs are single-player (2048, Atari, LunarLander, CartPole, Pendulum).

For our Splendor variant (hidden deck order, hidden deck-reserved cards) nothing here transfers. We would need root determinization — sample a consistent world (deck permutation + opponents' hidden reserves) per simulation batch and re-seed `reset` from it — which changes the tree/env contract that LightZero's C++ code bakes in.

## reuse_for_us
Do not adopt the framework; write the bespoke ~500-line PUCT/Gumbel tree, but port three specific pieces from LightZero rather than re-deriving them.

Why not adopt:
1. Two players are baked in at every layer — the C++ assert, the negamax backup, `players=[1,2]` in every env, and the collector's `reward_shaping`. Our 4-player individual / 1v2 / 2v2 modes need a value *vector* and per-seat backup. That means rewriting the node struct, the backup, the selection Q lookup, the collector credit assignment, and the target construction. At that point nothing of the original tree survives.
2. The Gumbel AlphaZero C++ core carries at least four bugs that specifically bite a 65-action varied-legal-action space (see pitfalls), plus a build that requires editing absolute macOS paths in `make.sh` and a `sys.path.append('/Users/your_user_name/code/LightZero/...')` still sitting in gumbel_alphazero.py:251 and 322. Its Python fallback is the wrong algorithm and crashes on arity (returns 2 values, unpacked into 3 at line 302).
3. Chance nodes exist only in StochasticMuZero (learned model, single-player, never combined with Gumbel), and hidden information is not addressed at all — so the two features our game most needs are exactly the two the Gumbel path lacks.
4. AlphaZeroModel is CNN-only: `observation_shape=(C,H,W)` with flatten sizes computed from H and W (lzero/model/alphazero_model.py:105-116). There is no `alphazero_model_mlp.py` (MuZero has one). Our flat Splendor feature vector needs a new model class regardless.
5. Debugging a C++/pybind11 tree we did not write, against a Node.js rules oracle and a bit-exact Python engine we did, is strictly worse than owning ~500 lines of NumPy/Python we can assert on.

What to port (Apache-2.0, attribution required):
- `get_sequence_of_considered_visits` + `get_table_of_considered_visits` — ctree_gumbel_muzero/lib/cnode.cpp:1041-1094, ~55 lines. This is the fiddly sequential-halving visit schedule; it is a faithful mctx transliteration and is correct. Port verbatim to Python and precompute the table once per (max_num_considered_actions, num_simulations) pair, not per simulation.
- `score_considered` — cnode.cpp:1096-1130, ~35 lines. Port, but pass **real logits** (not softmax probabilities) and keep `penalty` outside the `max`.
- `qtransform_completed_by_mix_value` + `compute_mixed_value` + `rescale_qvalues` — cnode.cpp:934-1038, ~85 lines. The completed-Q machinery. Port; use mctx defaults maxvisit_init=50, value_scale=0.1, gumbel_scale=1.0 (LightZero's 10.0 is a compensation for its probability/logit mix-up).
- The architectural pattern from `get_next_actions_batch` / `_batch_expand_leaf_nodes` — mcts_alphazero.cpp:236-330. Run N independent trees in lockstep, descend all to leaves, issue ONE batched network forward per simulation step across all N. This is the single most valuable idea in the repo for a real-model AlphaZero and it is exactly what their Gumbel variant lacks. On 4x A100 with 16 CPU cores/GPU, run 64-256 self-play games per rank in lockstep and the GPU stays saturated.

Our design, concretely: node stores `value_sum: np.ndarray[n_seats]` and `visit_count: int`; backup adds the whole vector at every node on the path (max^n / value-vector backup, which reduces exactly to negamax for n=2 zero-sum); child selection at a node uses `q[seat_to_play(node)]`; terminal leaves write the true per-seat outcome with the 1v2 (solo 15 vs duo 34 combined, winner by excess) and 2v2 (team total > 30 plus second-score condition, revocable) rules folded into the per-seat scalar so the tree never needs to know about coalitions. Value head outputs 4 seat-values, masked/padded for 2- and 3-player games; policy head outputs 66 logits (65 + an explicit PASS, see pitfalls). Chance nodes: with a real rules oracle, prefer root determinization over learned chance encoding — sample a deck permutation + opponent hidden reserves per simulation (or per block of simulations) and run a perfect-information tree in that world; average the root statistics. Sequential halving at the root is orthogonal to this and composes cleanly. For the RTX 3060 / 2 s per move: batch-1 forwards on a small residual MLP are ~1 ms, and our Python engine's step/reset are tens of microseconds, so 200-600 simulations per move is realistic — well above the 50 LightZero uses.

## ideas_to_steal
- Sequential-halving visit schedule, verbatim: get_sequence_of_considered_visits / get_table_of_considered_visits (ctree_gumbel_muzero/lib/cnode.cpp:1041-1094, ~55 lines). Precompute the table ONCE per (max_num_considered_actions, num_simulations) — LightZero rebuilds it inside every root child selection, i.e. once per simulation (mcts_gumbel_alphazero.cpp:163), which is pure waste.
- Completed-Q with mixed value: qtransform_completed_by_mix_value + compute_mixed_value + rescale_qvalues (cnode.cpp:934-1038). Fill unvisited children with (raw_value + N * sum_a pi_a q_a / sum_a pi_a) / (1 + N), min-max rescale, then scale by (maxvisit_init + max_visits) * value_scale. This is what lets Gumbel work at 50 sims with a 65-action space where most children are never visited — directly applicable to us.
- Batched lockstep trees, one network call per simulation step: get_next_actions_batch / _batch_expand_leaf_nodes (mcts_alphazero.cpp:186-330). N independent roots descend to leaves, then a single batched forward. This is the difference between a GPU at 3% and at 90% utilisation for a real-model AlphaZero, and it is the pattern our self-play loop should be built around from day one.
- Scatter-the-target-into-the-full-action-space pattern for varied legal-action sets: game_buffer_muzero.py:708-800 and the `action_type='varied_action_space'` branch — build a zero vector of size action_space_size and write the visit/improved-policy mass only at legal indices, so the policy-head cross-entropy has a stable shape while illegal actions get exactly zero target. We need this for 65 (66) actions with wildly varying legal sets.
- Storing the *improved policy* (softmax(logits + completed_q)) as the policy target instead of the visit-count distribution (gumbel_alphazero.py:547-575, gumbel_muzero.py:575-577). At 50-200 simulations over 65 actions the visit histogram is far too sparse to be a good target; the completed-Q policy is dense and low-variance. This is the main practical win of Gumbel for a wide action space and is worth adopting even if we keep plain PUCT selection.
- Real-env MCTS via reset-from-snapshot rather than deepcopy (mcts_alphazero.cpp:461-486 and ptree_az.py:222-236): each simulation resets the simulator to the root snapshot and replays only the tree descent. With our bit-exact Python engine this avoids per-node deepcopy entirely and composes naturally with determinization (reset to snapshot + a sampled hidden-state assignment).
- The env-interface contract itself is a good checklist for wiring any new game into an AlphaZero tree: reset(start_player_index, init_state, ...), step(action), legal_actions (property), get_done_winner() -> (done, winner[, reward, eval_return]), current_state() -> (raw, scaled), action_space.n, current_player, next_player, battle_mode / battle_mode_in_simulation_env. See zoo/board_games/tictactoe/envs/dummy_any_game_env.py — a deliberately minimal template that also shows the `non_zero_sum=True` escape hatch for games whose terminal values do not sum to zero (which our 1v2 'winner by excess' mode needs).
- Doubling num_simulations at evaluation relative to collection (gumbel_alphazero.py:320) — cheap way to buy strength at eval/inference time without changing the trained net; matches our asymmetric budget (cheap self-play on A100s, 2 s/move on a 3060).

## pitfalls
- Gumbel vector hard-coded to 36 entries and generated ONCE in the constructor: `gumbel(_generate_gumbel(gumbel_scale, gumbel_rng, 36))` — mcts_gumbel_alphazero.cpp:57, with the correct `simulate_env.action_space.n` line commented out right beside it. With our 65 actions this is an out-of-bounds read in `_score_considered` (`gumbel[i]`, line 428). Even at 36 it is wrong: the Gumbel noise is never resampled per move or per root.
- Gumbel seed is a hard-coded constant, not config: `this->gumbel_scale = 10.0; this->gumbel_rng = 0.0;` inside the C++ CNode constructors — ctree_gumbel_muzero/lib/cnode.cpp:61-63 and 86-89. Every root in every game gets the identical deterministic Gumbel vector. mctx splits an rng_key per search. If we port this code, resample per root.
- Out-of-bounds index in interior selection: `_select_interior_child` builds `to_argmax` densely over children (size == #children) but then indexes it by the raw action id, `to_argmax[action_tmp]` — mcts_gumbel_alphazero.cpp:221. Any node where max legal action id >= #children reads past the end of the vector. On a 65-action space with ~10-30 legal actions this is essentially every interior node. The Gumbel MuZero version indexes by legal-action position and is correct (cnode.cpp:775-786).
- Dead softmaxes in the AlphaZero Gumbel variant: `probs_softmax = softmax(probs, 1)` is computed then never used, and raw `probs` go into `to_argmax` (mcts_gumbel_alphazero.cpp:199-208); likewise `priors_softmax` is computed then the un-softmaxed `priors` are passed to `_compute_mixed_value` (lines 265-267). The MuZero version does apply the softmax in both places (cnode.cpp:773, 1013). Do not copy the AlphaZero file.
- Probabilities used where logits are required: `_score_considered` and `score_considered` add `child->prior_p`, which is a softmax probability in [0,1] (AlphaZeroModel.compute_policy_value returns softmax, lzero/model/alphazero_model.py:185; CNode::expand normalises to `policy[a]/policy_sum`, cnode.cpp:143-146). mctx adds raw `prior_logits`. With gumbel_scale=10 the prior term is numerically erased from root selection. Either use logits with gumbel_scale=1, or you are effectively doing uniform-random root exploration.
- Dirichlet root noise is identical every single call: `std::default_random_engine generator;` is default-constructed (fixed default seed) inside `_add_exploration_noise` — mcts_gumbel_alphazero.cpp:79 AND the maintained mcts_alphazero.cpp:92. So the C++ AlphaZero path has no effective root exploration noise at all. The Python ptree_az.py:435-441 uses np.random.dirichlet and is fine.
- Temperature is a mathematical no-op in both C++ trees: `visit_count_to_action_distribution` does `normalized_visits[i] = visits[i] / temperature` then normalises by the sum (mcts_gumbel_alphazero.cpp:638-664; mcts_alphazero.cpp:607-630). Dividing every entry by T and renormalising returns the raw visit distribution regardless of T. The Python version correctly uses `visits ** (1/T)` (ptree_az.py:253; lzero/policy/utils.py:659). Any temperature-annealing schedule against the ctree is silently inert.
- `num_considered = min(max_num_considered_actions, num_simulations)` — mcts_gumbel_alphazero.cpp:166 and cnode.cpp:727. mctx uses `min(max_num_considered_actions, num_actions)`. When a position has fewer legal actions than max_num_considered_actions (common in Splendor early game and after the 10-token cap bites), the halving schedule addresses actions that do not exist.
- No node with zero legal children is handled. ptree_az.py:355-362 sets `child = node` and returns `action = None`, after which `_simulate` treats the node as a leaf and calls `_expand_leaf_node` on an ALREADY-expanded node, overwriting `node.children` with fresh zero-count Nodes and discarding the subtree; the C++ path does `if (action == -1) break;` then re-expands and leaks. Our rare stuck seat (10 tokens, 3 reserved, nothing affordable) would hit exactly this. Add an explicit PASS action (65 -> 66) rather than relying on any tree to cope with an empty legal set.
- Gumbel AlphaZero has no working Python path: the `mcts_ctree=False` branch imports `lzero.mcts.ptree.ptree_az.MCTS` (gumbel_alphazero.py:264-268, 334-338), which is the vanilla PUCT tree and whose `get_next_action` returns 2 values, while the caller unpacks 3 (`action, mcts_probs, improved_probs = ...`, line 302). It raises ValueError immediately. There is no Gumbel implementation in lzero/mcts/tree_search/mcts_ptree.py at all.
- Build friction: ctree_alphazero and ctree_gumbel_alphazero are pybind11+CMake and are NOT part of setup.py (which only cythonizes .pyx files, setup.py:60-125). lzero/mcts/ctree/ctree_gumbel_alphazero/make.sh literally contains `cd /Users/<your_user_name>/code/LightZero/...` and `-DCMAKE_OSX_ARCHITECTURES="arm64"`, and gumbel_alphazero.py:251 and :322 still do `sys.path.append('/Users/your_user_name/code/LightZero/lzero/mcts/ctree/ctree_gumbel_alphazero/build')`. The plain alphazero.py was fixed to use `find_and_add_to_sys_path` (lines 235-238); the Gumbel one was not.
- Maintenance signal: `git log` on lzero/mcts/ctree/ctree_gumbel_alphazero/ shows exactly two commits — 1809d3f (2024-04-10, PR #212, the original) and 0684222 (2026-08-24, a memory-leak sweep across all AlphaZero ctree variants). lzero/policy/gumbel_alphazero.py's last substantive change is dd7a5eb (2024-11-15); 6bb8f5f (2025-10-24) was a mechanical ENV_REGISTRY refactor. Zero tests reference Gumbel anywhere in lzero/mcts/tests or lzero/policy/tests, and .github/workflows/test.yml does not exercise it. Treat this module as sample code, not a dependency.

# Literature brief: AlphaZero-style methods for multiplayer, imperfect-information board games (Splendor variant design)

## url
https://www.google.com/search?q=alphazero+multiplayer+imperfect+information+board+game

## kind
literature-synthesis (8 topics; 5 repos read as code, papers via search snippets only)

## summary
ACCESS CAVEAT, READ FIRST: arxiv.org, frontiersin.org, pmc.ncbi.nlm.nih.gov, lamsade.dauphine.fr, openreview.net, diva-portal.org, ar5iv and rlg.mlanctot.info are ALL blocked by the egress proxy. I opened no PDF for any of the eight target papers. Every paper-level claim below is from WebSearch snippets and is marked [SNIPPET]. To compensate I cloned and read five relevant codebases; those claims are marked [CODE] with file paths and line numbers and are the load-bearing part of this brief.

Headline for our design: the literature splits into two camps, and the camp that wins depends almost entirely on how much per-move search you can afford. (1) Search-free policy-gradient (Big 2 PPO, Generals.io) reaches strong/superhuman play in imperfect-information multiplayer games with NO tree search at inference — which fits our 2 s/move RTX-3060 budget perfectly. (2) AlphaZero+PIMC (AlphaZe**) works but is brutally search-hungry: [SNIPPET] it wins 36% at 800 nodes/turn and 59.6% at 25,000 nodes/turn in Barrage Stratego — a 31x search increase to cross 50%. The one published AlphaZero-style attempt at Splendor specifically [CODE, seal256/splendor] failed to train a working value head at all and could only reach stable self-play after reducing the win condition from 15 points to 5.

That last data point is the most important single finding in this brief: it is the closest prior work to our exact task, and it is a negative result. Splendor's long horizon, large branching factor and sparse terminal reward defeated a straightforward AlphaZero port. Our project should treat "AlphaZero on Splendor works" as an unproven hypothesis, not a baseline, and should hedge with a policy-gradient path.

## algorithm
(1) AlphaZe** — Bluml, Czech, Kersting, Frontiers in AI 2023 [CODE for the algorithm, SNIPPET for results].
The repo is github.com/BluemlJ/AlphaZe, a fork of CrazyAra. The actual mechanism, read from source:
- Determinization happens inside state cloning. engine/src/environments/stratego_related/strategostate.cpp:174-178 — `StrategoState* StrategoState::clone()` carries the comment "carefull clone will be init a random perfect information state". So each clone samples a fresh consistent world from the information set. A separate `openBoard()` (line 181+) lowercases the FEN to expose the true state — that is the cheating oracle used for the "TrueSight" upper-bound baseline (engine/src/uci/crazyara.h:261, `kTrueSight = 6`).
- The PIMC ensemble is engine/src/agents/mctsagentbatch.cpp. `MCTSAgentBatch::evaluate_board_state()` loops `numberOfAgents` times (line 70); each iteration clones the state (line 73 — a new determinization), runs a full independent AlphaZero MCTS (line 103), and stores the eval.
- Agent variants are enumerated at crazyara.h:255-263: kBatch3/kBatch5 (3 or 5 determinizations, full node budget each) and kBatch3_reducedNodes/kBatch5_reducedNodes ("the amount of nodes are splitted between all agents"). The split is literally `searchLimits->nodes = tmp/numberOfAgents` (mctsagentbatch.cpp:99-101). This is the fixed-budget variant and is the one relevant to us.
- Combination is NOT a majority vote despite the header comment. Lines 161-199: it sums policyProbSmall, childNumberVisits and qValues across determinizations, then picks the SINGLE determinization whose policy is closest (L1) to that combined vector (`diffs`, `min_element`, `stateIdx`) and copies that whole eval into evalInfo. It is a medoid-of-policies selection, not an average. Note lines 178-186 do `combinedPolicy[j] += combinedPolicy[j]/numberOfAgents`, i.e. sum*(1+1/N), not the mean — so the "average" the medoid is measured against is scaled by ~N+1 while each candidate policy sums to 1. This looks like a real bug and it distorts the selection.
[SNIPPET] The paper frames (PC-)PIMC as "the simplest possible change to AlphaZero to extend it to imperfect information games", trains purely by RL with no supervised bootstrapping, and evaluates on Stratego, Barrage Stratego and DarkHex. I could not open the paper, so I have no first-hand text on its IS-MCTS comparison or its strategy-fusion/non-locality discussion; snippets only assert the PIMC-vs-belief framing and the P2SRO/DeepNash comparison.

Expert Iteration (ExIt) + CNN for 4-player Catan. Snippets state: features are split into 29 channels "to prevent convolution from processing them uniformly", and a 5x3 kernel is used "to make neighbors comparable to actual neighbors on the hexagonal Catan board". (3) Charlesworth 2018, Big 2 [CODE — this is the best-documented source in the brief].
Repo github.com/henrycharlesworth/big2_PPOalgorithm, read in full.
- No search at all. PPO with a clipped surrogate, value clipping, entropy bonus, global grad-norm clipping, Adam eps=1e-5 (PPONetwork.py, class PPOModel).
- Network is a plain MLP, not a resnet: X -> fc1(512, relu) -> fc2(256, relu) -> policy head (1695 logits); the value head branches off h1 -> fc3(256, relu) -> vf(1) (PPONetwork.py lines ~15-22). Scalar value.
- Illegal-action masking is additive on logits: `available_moves` is a vector of 0 / -inf added to the policy logits (`availPi = tf.add(pi, available_moves)`), with the comment "0 if action is available, -inf if not". Sampling uses the Gumbel-max trick: `argmax(availPi - log(-log(u)))`.
- Action space 1695 = 13 singles + 33 pairs + 31 triples + 330 two-pair/quads + 1287 five-card + 1 pass (enumerateOptions.py:6, `nActions = [13,33,31,330,1287,1694]`, `passInd = 1694`).
- Observation 412 dims (big2Game.py:76-79).

(5) Gumbel planning — Danihelka, Guez, Schrittwieser, Silver, ICLR 2022 [SNIPPET + CODE for the reference implementation].
[SNIPPET] The diagnosis: AlphaZero's policy target is the normalized visit distribution, which is only a valid improvement operator when the root is well covered; with few simulations most root actions are never visited, so the target can be worse than the prior and training can regress. The fix has three parts: (a) at the root, sample m actions WITHOUT replacement via the Gumbel-top-k trick on the policy logits, (b) allocate the simulation budget across them with Sequential Halving, (c) build the policy target from COMPLETED Q-values — backed-up Q for visited actions, the value network's estimate for unvisited ones — rather than from visit counts. This yields a monotone policy-improvement guarantee, so more simulations never hurt and few simulations still help. The final root action is taken deterministically (the Sequential Halving survivor), not sampled from visits.
[SNIPPET] Worked budget: 200 simulations with m=16 gives four halving levels of 16/8/4/2 actions receiving 3/6/12/28 simulations each.
[CODE] google-deepmind/mctx defaults: `max_num_considered_actions = 16`, `gumbel_scale = 1.0` (mctx/_src/policies.py:136-137, with the note at line 171 that evaluation on perfect-information games can use gumbel_scale=0.0). The Q-transform (mctx/_src/qtransforms.py:92-94, 141-145) uses `value_scale = 0.1`, `maxvisit_init = 50.0`, `rescale_values = True`, computing `(maxvisit_init + max_visits) * value_scale * completed_qvalues` — note mctx's default value_scale of 0.1 differs from the c_scale=1.0 often quoted from the paper.

(6) KataGo training tricks [CODE — exact constants from the repo].
- Playout cap randomization, cpp/configs/training/selfplay8a.cfg:39-41 and selfplay1.cfg:60-62 (identical in both, so these values are stable across generations): `cheapSearchProb = 0.75`, `cheapSearchVisits = 100`, `cheapSearchTargetWeight = 0.0`, against `maxVisits = 600` (selfplay8a.cfg:93). So 75% of moves get a 100-visit search that contributes ZERO policy-training weight, 25% get the full 600-visit search and supply the targets. Wired in cpp/program/play.cpp:1132-1141; `cheapSearchProb *= 0.5` under some conditions at line 1128.
- Also `reducedVisitsMin = 100`, `reducedVisitsWeight = 0.1` (selfplay8a.cfg:46-47).
- Policy-surprise weighting: `policySurpriseDataWeight = 0.5`, `valueSurpriseDataWeight = 0.1` (selfplay8a.cfg:54-55). Per docs/KataGoMethods.md: half the training weight is spread uniformly, the other half is distributed proportional to the KL divergence between the policy prior and the policy target; a position is written `floor(w)` times plus once more with probability `w - floor(w)`.
- Forced playouts / policy target pruning: the modern implementation is `Search::pruneNoiseWeight`, cpp/search/searchupdatehelpers.cpp:495-539. Children are walked in policy order; for each child, if its utility is below the running weighted average of the children before it AND it holds more than 2x its raw-policy share of the weight, the excess is shaved: `weightShareFromRawPolicy = weightSumSoFar * rawPolicy / rawPolicySumSoFar`; `lenient = 2.0 * weightShareFromRawPolicy`; if `oldWeight > lenient` then `weightToSubtract = (oldWeight - lenient) * (1 - exp(-utilityGap / noisePruneUtilityScale))`, capped at `noisePruningCap`. Defaults `noisePruneUtilityScale = 0.15`, `noisePruningCap = 1e50` (effectively uncapped) at cpp/search/searchparams.cpp:34-36; enabled in two preset param sets at lines 318 and 355. This removes Dirichlet-noise-induced over-visitation from the policy target.
- Score utility (selfplay8a.cfg:144-150): `winLossUtilityFactor = 1.0`, `staticScoreUtilityFactor = 0.00`, `dynamicScoreUtilityFactor = 0.40`, `dynamicScoreCenterZeroWeight = 0.25`, `drawEquivalentWinsForWhite = 0.5`. Search utility is win/loss at weight 1.0 PLUS 0.40x a dynamically-recentered score term — this is what makes KataGo play for margin, not just P(win).
- Auxiliary short-term value/score targets (docs/KataGoMethods.md): exponentially-averaged future MCTS values, `(1-lambda) * sum_{t'>=t} MCTS_value(t') * lambda^(t'-t)`, with three lambdas giving mean horizons of ~6, ~16 and ~50 turns on 19x19, scaled down proportionally to board area for smaller boards. The net also predicts its own squared error on these, and those predicted uncertainties reweight playouts (lambda ~5/6 on 19x19), with a small minimum baseline uncertainty capping the max weight.
- Dirichlet noise is specified as a TOTAL concentration, not a per-move alpha: `rootDirichletNoiseTotalConcentration = 10.83`, `rootDirichletNoiseWeight = 0.25` (selfplay8a.cfg:132-133). alpha_i = 10.83 / num_legal_moves. This reproduces AlphaZero's Go alpha=0.03 at 362 moves and generalizes cleanly to variable legal-move counts.

(7) AlphaStar league / PFSP [SNIPPET ONLY]. ## multiplayer_handling
This is where the code was most valuable, because the papers are blocked and the design choice is real for us.

A. Per-player VALUE VECTOR with maxn backup — the standard answer [CODE, petosa/multiplayer-alphazero, NeurIPS 2019 Deep RL Workshop].
- The value head emits one scalar per player: `self.v_head = torch.nn.Linear(512, np.prod(v_shape))` and `v = torch.tanh(self.v_head(flat).view(this_v_shape))` (models/senet.py:92, 119), with v_shape = (num_players,).
- MCTS backs up the WHOLE vector and each node consumes only its own component (mcts.py:42-47):
    scores = self.simulate(s_prime)
    v = scores[current_player]        # index in to find our reward
    stats[best_a_idx, 2] = (n*q+v)/(n+1)
    stats[best_a_idx, 1] += 1
    return scores                      # vector propagates further up
  At a leaf, `p, v = self.nn.predict(s)` and the vector v is returned unchanged (mcts.py:55-60). Terminal states also return a vector (mcts.py:50-52). This is textbook maxn: every node maximizes its OWN component, no paranoid or minimax assumption.
- Terminal encoding for 3 players (games/tictacmo.py:32-43): `reward = -np.ones(num_players); reward[p] = 1` for a win, `np.zeros(num_players)` for a draw. Note this is winner=+1 / losers=-1, which sums to -1 for 3 players — it is NOT sum-to-zero. It works, but it means the value head's outputs are not constrained to a simplex and the net must learn the consistency itself.
- Losses (neural_network.py:52-69): `v_loss = ((v_pred - v_gt)**2).sum()` (MSE on the whole vector), `p_loss = -sum(gt * log_softmax_over_valid_actions)`. Total = p_loss + v_loss, Adam lr=1e-3, weight_decay=1e-8, batch 64.
- PUCT: `U = cpuct*P*sqrt(N.sum() + 1e-6)/(1 + N)` (mcts.py:35). The 1e-6 "epsilon_fix" is deliberate — without it U is 0 when all N=0 and the priors are ignored at expansion; with it the prior steers the very first visits. Worth copying.
- Honest gap: the file's own header comments admit "No Dir noise being added" — this implementation has NO Dirichlet root noise. [SNIPPET] The paper reports evaluation on two simple 3-player games and claims it "learns successfully and consistently outperforms Monte Carlo tree search"; I could not retrieve the numbers.

B. Per-player value vector also appears in the Splendor repo's interface [CODE, seal256/splendor].
pysplendor/mcts.py: `class Value(ABC)` with `predict(...)` documented as "Estimates the value of the game_state for each player", and backup does `node.wins += rewards[node.acting_player]` (line 181, 189, 255). Same maxn pattern. Rollouts return `state.rewards()`, a vector (src/mcts.cpp:157-168).

C. Shared-net-across-seats with SCALAR value and stride-N GAE — the policy-gradient answer [CODE, Big 2].
This is the cleanest multiplayer credit-assignment trick I found and it maps almost exactly onto our turn-based game.
- One network plays all four seats: `self.playerNetworks[1] = self.playerNetworks[2] = self.playerNetworks[3] = self.playerNetworks[4] = self.trainingNetwork` (mainBig2PPOSimulation.py:33).
- The value head is a SCALAR from the acting seat's own perspective (not a vector) — legitimate because the observation is egocentric (see hidden_info_handling).
- Because turn order is strictly cyclic with 4 players, the rollout buffer interleaves seats, and GAE is computed per seat by striding 4 (mainBig2PPOSimulation.py:139-145):
    for k in range(4):
        lastgaelam = 0
        for t in reversed(range(k, endLength, 4)):
            nextNonTerminal = 1.0 - mb_dones[t]
            nextValues = mb_values[t+4]          # SAME seat's next state, not the next player's
            delta = mb_rewards[t] + gamma*nextValues*nextNonTerminal - mb_values[t]
            mb_advs[t] = lastgaelam = delta + gamma*lam*nextNonTerminal*lastgaelam
  `mb_values[t+4]` is the acting seat's own next decision point. Getting this wrong (using t+1) would bootstrap a seat's value off an opponent's value and silently destroy learning.
- Terminal credit is fanned back to all four seats at their own last decision points (lines 108-117): on `dones[i]`, the last four buffer entries each receive `reward[mb_pGos[-k][i]-1] / rewardNormalization`, and `mb_dones[-2..-4]` are forced True so GAE does not bootstrap across the game boundary for seats that already finished.
- Because that fan-back needs 4 steps of lookahead, the last 4 timesteps are carried into the next rollout via prevObs/prevGos/... (lines 59-67, 78-90, 121-128), with `endLength = nSteps - 4` on the first call and `nSteps` after. This is exactly the bookkeeping our 3- and 4-player modes will need.

D. Reward shape: margin, not binary [CODE, Big 2, big2Game.py:343-345].
    self.rewards[i-1] = -1*nC          # each loser: minus cards left in hand
    self.rewards[winner-1] = totCardsLeft   # winner: sum of all opponents' remaining cards
A genuinely zero-sum MARGIN reward, then divided by `rewardNormalization = 5.0` with the comment "so reward ranges from -1.0 to 3.0" (mainBig2PPOSimulation.py:54). Not win/loss. This is the single most transferable choice for our 1v2 ("winner by excess") and 2v2 ("team total > 30") modes, which are explicitly margin-defined.

E. KataGo's score utility is the search-side analogue of D: utility = 1.0*winloss + 0.40*dynamic_score, so the search itself prefers larger margins among equally-winning lines.

F. Teams: I found NO published treatment of 2v2 or 1v2 asymmetric-team AlphaZero in any source I could reach. Every multiplayer source above is free-for-all individual play. Our 1v2 and 2v2 modes are genuinely uncovered by this literature; the value-vector formalism extends to them naturally (emit 3 or 4 per-seat values, define the terminal vector by the team rule) but nobody has validated it.

## hidden_info_handling
Three distinct strategies appear, and they sit at very different points on the compute curve.

1. PIMC / determinization — sample worlds, search each with a perfect-information searcher [CODE, AlphaZe**].
As described in `algorithm`: `clone()` resamples a consistent world (strategostate.cpp:174-178), N independent AlphaZero searches run (mctsagentbatch.cpp:70-106), and results are combined by medoid selection (lines 161-199). The `_reducedNodes` variants divide the node budget by N so total compute is fixed.
Known theoretical defects of PIMC (strategy fusion — the searcher assumes it can act differently in worlds it cannot actually distinguish; and non-locality) are the standard critique. [SNIPPET] The paper reportedly argues PIMC is nonetheless "surprisingly strong" as a baseline; I could not read its treatment of these two failure modes, so I am not going to characterize its argument.
Relevance to us is limited but real: our hidden information is small and cheap to sample (deck order + opponents' deck-reserved cards). A determinization is a single shuffle of the unseen card multiset — far cheaper to sample than a Stratego piece assignment. But see reported_strength: PIMC needs a lot of nodes to pay off.

2. Egocentric, seat-relative information-set encoding — no belief modelling at all [CODE, Big 2]. This is the approach I would actually recommend for us.
big2Game.py maintains a separate 412-dim observation per seat, and each contains ONLY that seat's information set:
- Dims 0..285: the acting player's OWN 13 cards, 22 features each (13 value one-hot, 4 suit one-hot, then 5 combinatorial flags: inPair, inThreeOfAKind, inFourOfAKind, inStraight, inFlush) — `fillNeuralNetworkHand`, lines 97-122. Note the hand-crafted combinatorial flags; the net is told which cards participate in which hand types rather than having to learn it.
- Dims 286..366: three 27-dim opponent blocks, addressed RELATIVELY as nPlayer / nnPlayer / nnnPlayer computed by decrementing with wraparound (lines 127-137, 165-175). Each block holds a 13-dim one-hot of the opponent's CARD COUNT plus 8 "cards of note" flags for the high cards indices 45-52 that have been publicly played (`cardsOfNote = np.intersect1d(prevHand, np.arange(45,53))`, lines 176-181). Public information only — no leakage.
- Remaining dims: last-played-hand and pass-state features (phInd = 22*13 + 27*3 + 16 = 383, so 29 dims).
Two lessons here. First, the encoding is a strict information set, so a single network can be trained on all seats without cheating. Second, opponents are indexed by RELATIVE seat offset, never absolute seat id. That is what makes one set of weights valid in every seat and is why `self.playerNetworks[1..4] = self.trainingNetwork` is sound.

3. Nothing — treat partial observability as noise and let a recurrent-free policy handle it [SNIPPET, Generals.io]. A ViT policy on the observed map with sparse win/loss reward, no belief state, no search, reaching #1 on a 5,000-player ladder. Evidence that in some strongly-imperfect-information games raw self-play policy gradient simply absorbs the uncertainty.

Nobody in the sources I could reach uses an explicit learned belief/opponent model. [SNIPPET] There is adjacent work I saw titled but could not open ("Neural Network-Based Information Set Weighting for Playing Reconnaissance Blind Chess"; "Efficiently Training Neural Networks for Imperfect Information Games by Sampling Information Sets") that appears to weight sampled information sets with a net — that is the natural upgrade path from plain PIMC if we ever want one.

For our variant specifically: the hidden state is unusually small. Board-reserved cards are public; only deck order and opponents' deck-reserved cards are hidden, and a deck-reserved card is drawn from a known remaining multiset. So (a) the information set is compactly encodable — per-opponent counts of deck-reserved cards plus the public remaining-deck composition — and (b) if we ever want PIMC, sampling a world is one shuffle. Option 2 (egocentric info-set encoding, no search-time determinization) is by far the cheapest correct thing and is what Big 2 shows to be sufficient in a comparable regime.

## reuse_for_us
Concrete recommendations for the 65-action Splendor variant on 4x A100-40GB training / RTX 3060 with a 2 s move budget.

1. Run TWO tracks, and make the policy-gradient track the primary one. The 2 s/move on a 4 GB card is the binding constraint, and it is roughly what a few hundred NN evaluations cost, not tens of thousands. AlphaZe**'s 36% → 59.6% jump between 800 and 25,000 nodes says a PIMC/AlphaZero agent throttled to our inference budget will land in the weak part of its own curve. Big 2 and Generals.io both reach strong play with ZERO search at inference. Track A: PPO with a shared egocentric network (Big 2 recipe). Track B: Gumbel AlphaZero at a small simulation count. Gate the decision on measured 3060 throughput, not on which is more fashionable.

2. Adopt the Big 2 seat handling wholesale — it maps onto our modes almost line for line.
   - One network, all seats, egocentric observation. Encode opponents by RELATIVE seat offset (next, next-next, next-next-next), never absolute seat id (big2Game.py:127-137). For 1v2 and 2v2 add explicit role/team-relation planes (is-teammate, is-solo-opponent, my-role) so the same weights serve solo and duo seats.
   - Compute GAE per seat with stride = num_players and `nextValues = mb_values[t + num_players]` (mainBig2PPOSimulation.py:139-145). Our turn order is strictly cyclic, so this applies directly. Using t+1 here is the silent-killer bug.
   - Fan terminal reward back to the last decision point of every seat and force `done` on all of them (lines 108-117), carrying the trailing num_players timesteps between rollout segments (lines 121-128).
   - Handle our no-legal-move seat (10 tokens, 3 reserved, nothing affordable) as an explicit forced pass action in the 65-action space, so the stride-N interleaving stays exact. If instead the seat is skipped, the stride-4 assumption breaks and GAE silently mis-attributes. This is a real risk for us that Big 2 never faced.

3. Mask illegal actions additively on the logits: `logits + (0 or -inf)` (PPONetwork.py). With 65 actions and often only a handful legal, this matters far more than at 1695. Sample with the Gumbel-max trick as they do. Alternative (petosa's `get_valid_dist`) is log_softmax over the selected valid subset — equivalent, pick one.

4. Use a MARGIN terminal reward, normalized, not binary win/loss. Big 2 does exactly this (winner gets the sum of opponents' remaining cards, losers get minus their own; divided by 5.0). Our modes are already margin-defined: 1v2 is decided "by excess", 2v2 by "team total > 30" plus a second-score condition. Encode those excesses directly, scale to roughly [-1, 1], and you get a far denser learning signal than 15-points-or-bust. This also directly attacks the failure mode seal256 hit — Splendor's sparse point reward — and is the same idea Rinascimento's event-value functions were invented for [SNIPPET].

5. Value representation: emit a per-seat VALUE VECTOR (length = num players) with maxn backup if you go the search route (petosa mcts.py:42-47 is 6 lines and correct); emit a scalar from the acting seat's perspective if you go pure PPO (Big 2). Do not mix. For 2v2 the vector generalizes cleanly: terminal vector assigns the team result to both teammates. For 1v2, note the terminal vector will NOT be sum-to-zero (that is fine — petosa's is not either, tictacmo.py:34).

6. If you use AlphaZero-style search, take these KataGo settings as defaults rather than tuning from scratch:
   - Playout cap randomization at their exact ratio: 75% of moves at ~1/6 the visits with ZERO policy-target weight, 25% at full visits supplying the targets. Roughly 3x cheaper self-play.
   - Dirichlet alpha = 10.83 / (number of LEGAL moves at this node), weight 0.25. Our legal-move count swings wildly (a forced short take vs a wide-open turn), so a fixed alpha is wrong. Note seal256 used alpha=0.03 — the Go 19x19 value — with only 43 actions; at ~10 legal moves that is essentially no noise at all, a plausible contributor to their training trouble.
   - Score utility: weight the search's utility as winloss*1.0 + 0.40*margin_term so the agent plays for excess in 1v2/2v2 rather than settling for a bare win.
   - `pruneNoiseWeight` (searchupdatehelpers.cpp:495-539) to strip noise-induced over-visitation from the policy target.
   - Auxiliary targets: our analogue of ownership/score is per-seat final-score prediction, per-seat card-count, and time-to-15. Cheap heads, dense gradient, exactly the sparse-reward remedy Splendor needs.

7. If you use search, use GUMBEL, not vanilla PUCT-with-visit-count targets. This is the single highest-value technical choice given our inference budget. With 65 actions and a 2 s budget you will be running on the order of 100-400 simulations, which is precisely the regime where AlphaZero's visit-count policy target is unreliable and where Gumbel's completed-Q target has a monotone improvement guarantee. Start at mctx defaults: m=16 considered root actions, gumbel_scale=1.0, value_scale=0.1, maxvisit_init=50.

8. Chance nodes: cap them hard. seal256's biggest single measured gain (+400 Elo) came from restricting chance-node branching, and their C++ exposes `max_chance_children` (src/mcts.h:27, default 100) with `node->children.resize(params.max_chance_children)` after shuffling (src/mcts.cpp:151-153). Our deck draws after each buy/reserve are exactly this. Cap to 1-4 children. Be aware their reward downscaling through chance nodes (`rewards = [r/len(parent.children) for r in rewards]`, pysplendor/mcts.py:77-79) systematically shrinks values behind chance nodes — I would not copy that part.

9. Opponent pool: full AlphaStar league machinery is overkill for 2-4 seats, but keep PFSP's core: sample past checkpoints with weight proportional to (1 - win_rate_against_them)^(1/2) so you oversample opponents you are losing to. For 1v2 and 2v2, maintain SEPARATE pools per role (solo vs duo-member) — a solo-seat exploiter and a duo-seat exploiter are different agents, and a single pool will let one role's weaknesses hide. Note the [SNIPPET] Big 2 follow-up finding that current-policy self-play beat checkpoint self-play under a finite budget — so do not over-invest in the pool early; add it when plain self-play plateaus.

10. Evaluation: copy petosa's escalating ladder (main.py) — after each checkpoint, play the current net against heuristic-free MCTS at 10/20/40/.../1280 simulations. It gives a cheap, monotone, absolute strength curve without needing a human baseline, and it will tell you early whether you are on the seal256 trajectory (plateaus below strong MCTS) or the Big 2 one.

11. De-risk exactly the way seal256 did, but deliberately: keep a reduced-difficulty variant (e.g. win at 5 or 8 points instead of 15) in the test matrix from day one. If the full 15-point game will not train, you want to discover that against a working 5-point pipeline, not against a blank loss curve. Their experience says this is the likely failure mode, not an unlikely one.

## ideas_to_steal
- Stride-N per-seat GAE for turn-based multiplayer PPO: for k in range(N): for t in reversed(range(k, T, N)) with nextValues = mb_values[t+N] — recovers each seat's own trajectory from an interleaved buffer with one shared network and a scalar value head (big2_PPOalgorithm/mainBig2PPOSimulation.py:139-145). Directly applicable to our 2/3/4-seat cyclic turn order.
- Terminal-reward fan-back with trailing-window carryover: on done, assign each of the last N buffer entries its own seat's reward and force done on all of them; carry the last N timesteps into the next rollout segment (same file, lines 108-128). This is the non-obvious bookkeeping that makes multiplayer PPO rollouts correct.
- Zero-sum MARGIN terminal reward instead of binary win/loss, then divide by a constant to land in roughly [-1,1] (big2Game.py:343-345 + rewardNormalization=5.0). Maps onto our 1v2 'winner by excess' and 2v2 'team total > 30' rules and densifies Splendor's notoriously sparse point reward.
- Additive -inf logit masking for legal actions plus Gumbel-max sampling (PPONetwork.py). With 65 actions and few legal at any time, this is essential, and it keeps the entropy/neglogp math exact.
- Seat-RELATIVE opponent encoding (next / next-next / next-next-next), never absolute seat index (big2Game.py:127-137, 165-181). One weight set valid in every seat; the basis for training all seats with a single network.
- Hand-crafted combinatorial feature flags alongside raw card identity (inPair, inThreeOfAKind, inStraight, inFlush per card, big2Game.py:97-122). Our analogue: per-card affordability-now, affordability-after-one-take, gold-needed, noble-progress-contribution. Cheap, and it removes a lot of learning burden.
- KataGo playout cap randomization at its shipped ratio: cheapSearchProb=0.75 / cheapSearchVisits=100 / cheapSearchTargetWeight=0.0 against maxVisits=600 (cpp/configs/training/selfplay8a.cfg:39-41,93). ~3x cheaper self-play per usable training target.
- Dirichlet noise specified as a TOTAL concentration rather than a fixed alpha: alpha_i = 10.83 / num_legal_moves, weight 0.25 (selfplay8a.cfg:132-133). Correct under our wildly varying legal-move counts, where a fixed Go-style alpha=0.03 would mean essentially no exploration noise.
- KataGo score utility: search utility = 1.0*winloss + 0.40*dynamic_score with dynamicScoreCenterZeroWeight=0.25 (selfplay8a.cfg:144-150). Makes the SEARCH prefer margin, complementing a margin reward in training. Needed for 1v2/2v2 where excess decides the winner.
- pruneNoiseWeight: shave a child's weight when its utility is below the running weighted average AND it holds >2x its raw-policy share, by excess*(1-exp(-utilityGap/0.15)) (cpp/search/searchupdatehelpers.cpp:495-539). Removes Dirichlet-noise contamination from the policy target.
- Policy-surprise data weighting: half the training weight uniform, half proportional to KL(policy_prior || policy_target); write a position floor(w) times plus once more with probability w-floor(w) (docs/KataGoMethods.md). Concentrates capacity on positions where the net was wrong.
- Gumbel root planning for small simulation budgets: Gumbel-top-k sample m=16 root actions without replacement, allocate via Sequential Halving, build the policy target from COMPLETED Q-values (backed-up Q for visited, network value for unvisited), and play the survivor deterministically. mctx defaults max_num_considered_actions=16, gumbel_scale=1.0, value_scale=0.1, maxvisit_init=50.0. This is the right search algorithm for a 2 s / 4 GB inference budget.
- Per-player value VECTOR with maxn backup, in 6 lines: return the vector from leaves and terminals, and at each node use only v = scores[current_player] for its own running Q (petosa/multiplayer-alphazero/mcts.py:42-47, 55-60; v_head = Linear(512, num_players) with tanh, models/senet.py:92,119). The clean extension point for 1v2 and 2v2 terminal vectors.
- PUCT epsilon fix: U = cpuct*P*sqrt(N.sum() + 1e-6)/(1+N) so the prior actually steers the first visit instead of U collapsing to 0 when all N=0 (petosa/mcts.py:35). Matters a lot at low simulation counts.
- Hard cap on chance-node branching: shuffle children then resize to max_chance_children (seal256/splendor src/mcts.cpp:151-153). Their single largest measured gain (+400 Elo). Our post-purchase deck draws are exactly this; cap to 1-4.
- Zero-initialize the policy output layer so the net starts at a uniform policy (seal256/splendor train.py:127-128).
- NaN rollback guard: after each optimizer step, if any parameter is NaN, restore the pre-update parameters (big2 mainBig2PPOSimulation.py:186-192).
- Escalating-opponent evaluation ladder: after each checkpoint, play heuristic-free MCTS at 10/20/40/80/160/320/640/1280 sims (petosa/main.py). Cheap absolute strength curve with no human baseline needed.
- AlphaGo-Zero-style gating plus early stop: promote a new model only if win rate exceeds a threshold, keep the last 10 iterations of games in the buffer, stop after 12 non-improving iterations (seal256/splendor self_play.py).
- PFSP opponent sampling weight proportional to (1 - win_rate_against_snapshot)^(1/2), with SEPARATE pools per role for our asymmetric 1v2 modes [SNIPPET, AlphaStar].
- Fixed-budget PIMC: divide the node budget by the number of determinizations rather than multiplying total compute (AlphaZe mctsagentbatch.cpp:99-101). The only honest way to compare PIMC ensembles under our 2 s cap.

## pitfalls
- EVIDENCE CAVEAT, most important: arxiv.org, frontiersin.org, PMC, lamsade.dauphine.fr, openreview.net, diva-portal.org, ar5iv, dl.acm.org, link.springer.com and rlg.mlanctot.info are ALL blocked here. I read NO PDF for any of the eight target papers. Everything marked [SNIPPET] — including AlphaZe**'s 36%/59.6%, Generals.io's 4-days-on-4xH200 and 199-70, Gumbel's 16/8/4/2 schedule, and the PFSP exponent — is second-hand from search summaries and should be re-verified before it goes in a design doc or a paper.
- The only inspectable AlphaZero-style Splendor attempt (seal256/splendor) FAILED to train a usable value head: 'Training the state value function proved ineffective ... the added noise in node evaluations only degraded performance.' Their shipped net is policy-only. Assume our value head is the hard part, budget for auxiliary targets and margin rewards from the start, and do not plan as if AlphaZero-on-Splendor is a solved baseline.
- Same repo: stable self-play was only achievable after reducing the win condition from 15 points to 5, and even then the result 'still struggles to consistently defeat experienced human players.' Our 15-point target is materially harder than the only setting anyone got to train.
- PIMC is search-budget-hungry in a way that collides with our 2 s / RTX-3060-4GB inference budget. [SNIPPET] AlphaZe** moved from 36% to 59.6% only by going from 800 to 25,000 nodes per turn. Do not benchmark a PIMC agent at training-time budgets and then assume it survives deployment throttling.
- AlphaZe**'s ensemble combination has what looks like a real bug: mctsagentbatch.cpp:178-186 computes sum*(1 + 1/N) rather than the mean, so the 'combined' policy the medoid selection compares against is scaled by ~N+1 while each candidate sums to 1. Also, despite the enum comment saying 'majority vote', the code selects one determinization's eval wholesale (lines 188-199) rather than averaging. Do not port this combination rule; average the policies properly, or aggregate visit counts across determinizations.
